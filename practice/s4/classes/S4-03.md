# S4-03 — Logging estructurado

## Contexto

`S3-10` dejó logs funcionando en un archivo de texto plano. Sirve para leer secuencialmente, pero no para responder "¿qué pasó con el turno X específicamente?" sin hacer scroll manual por miles de líneas. Esta clase convierte los logs en algo filtrable — y es preparación directa para la observabilidad real de `S6`.

## Concepto mínimo

**Logs estructurados son datos, no prosa.** En vez de una línea de texto libre, cada entrada de log es un registro con campos consistentes (JSON, típicamente) que se puede filtrar, agrupar y consultar como si fuera una tabla.

```python
logger.info("turno_creado", extra={"turno_id": str(turno.id), "profesional_id": str(turno.profesional_id)})
```

**Nunca datos de pacientes en los campos** — la misma regla de `S3-10`, ahora aplicada también a los campos estructurados, no solo al mensaje. Es más fácil de romper por accidente en un log estructurado que en uno de texto libre, porque es tentador loguear el objeto completo "para tener contexto" — y el objeto completo incluye nombre y DNI.

**Niveles con intención, no por costumbre.** `DEBUG` para detalle que solo importa en desarrollo. `INFO` para operación normal (turno creado, recordatorio enviado). `WARNING` para algo recuperable pero digno de atención (el reintento de `S4-02`). `ERROR` para lo que de verdad rompió algo y necesita revisión.

**Un identificador de correlación** permite reconstruir todos los eventos de una misma operación (por ejemplo, todo lo que pasó al crear un turno específico) filtrando por un único campo, aunque los eventos hayan ocurrido en momentos distintos o en el comando de recordatorios de `S4-02`.

## Demostración

El mentor configura el logger para emitir JSON estructurado (con `python-json-logger` o un formateador simple propio), genera algunos eventos reales del proyecto, y muestra cómo filtrar el archivo de log por `turno_id` con una herramienta de línea de comandos (`jq`, o incluso `grep` sobre el JSON) para ver únicamente los eventos de un turno puntual.

## Laboratorio

Con guía: agregar un identificador de correlación (por ejemplo, un id de request) a los logs generados dentro de una misma petición HTTP.

## Ejercicio

Sin guía: agregar logging estructurado al comando de recordatorios de `S4-02` — éxito y fallo, por turno, con el `turno_id` como campo, sin ningún dato de paciente — y verificar filtrando los logs de una corrida específica.

## Challenge

Investigá `contextvars` de Python para propagar el identificador de correlación automáticamente a través de las funciones que se llaman dentro de una misma operación, sin tener que pasarlo como parámetro explícito en cada una.

## Project Task

1. Logging estructurado en las operaciones críticas del proyecto: creación de turno, cancelación, envío de recordatorio.
2. Auditoría explícita: confirmar que ningún campo de ningún log contiene datos de pacientes.
3. Commit: `Migrar a logging estructurado con contexto filtrable`.

## Evidencia — Definition of Done

- [ ] Los logs son estructurados (parseables), no texto libre.
- [ ] Resolviste un caso real (o simulado) de "qué pasó con este turno" filtrando logs por un campo específico, no leyendo todo el archivo.
- [ ] Auditaste que ningún campo de log contiene nombre, DNI, teléfono ni ningún otro dato de paciente.
- [ ] Los niveles de log (`INFO`/`WARNING`/`ERROR`) se usan con intención, no todo como `INFO`.

## Bibliografía de esta clase

No hay bibliografía nueva específica en castellano para logging estructurado en Python — la documentación oficial del módulo `logging` (`docs.python.org/es/3/library/logging.html`, ya asignada) cubre la base; el formato JSON estructurado es más una convención de la industria que un tema con libro propio.

## Nota sobre abstracción

Logging estructurado con identificadores de correlación es una práctica estándar en cualquier sistema en producción, independiente del lenguaje — es la base de lo que en sistemas más grandes se vuelve tracing distribuido (contenido de `S6`).
