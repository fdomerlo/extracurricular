# S4-02 — Procesos en segundo plano: recordatorios de turno

## Contexto

El consultorio quiere mandar un recordatorio el día anterior a cada turno. Hacerlo dentro del mismo request que crea el turno es un error concreto: el usuario que reserva queda esperando a que un servidor de email externo responda, y si ese servidor está caído, la reserva —que es válida— fallaría por una razón que no tiene nada que ver con ella.

## Concepto mínimo

**Separar la acción rápida de la lenta.** Crear el turno es rápido y debe confirmarse de inmediato. Enviar el recordatorio es lento, puede fallar, y no debería bloquear ni condicionar lo primero.

**La herramienta correcta para esta escala.** Un sistema con colas de mensajes (Celery + Redis) es la solución "de libro" para procesos en segundo plano — pero para un consultorio de tres usuarios, es infraestructura que no se justifica todavía (mismo criterio de `plan.md` §2: la complejidad se agrega por necesidad). La alternativa liviana: un *management command* de Django que corre por `cron` (ya usás cron desde `S3-10`), consultando qué turnos de mañana todavía no tienen recordatorio enviado.

```python
# management/commands/enviar_recordatorios.py
class Command(BaseCommand):
    def handle(self, *args, **options):
        turnos = Turno.objects.filter(fecha=manana(), recordatorio_enviado=False)
        for turno in turnos:
            try:
                enviar_email_recordatorio(turno)
                turno.recordatorio_enviado = True
                turno.save()
            except Exception as e:
                logger.warning(f"Fallo al enviar recordatorio para turno {turno.id}: {e}")
                # no se marca como enviado — se reintenta solo en la próxima corrida
```

**Idempotencia por diseño, no por suerte.** El campo `recordatorio_enviado` es lo que hace seguro correr el comando dos veces: un turno ya marcado no se reenvía. Un fallo simplemente deja el turno sin marcar, y la próxima corrida lo vuelve a intentar automáticamente — reintento gratis, sin código adicional.

**Un fallo individual no debe frenar el resto.** El `try/except` está *dentro* del loop, por turno — si falla el envío de uno, los demás igual se procesan.

## Demostración

El mentor escribe el comando, carga un turno de prueba para "mañana", lo corre, muestra el envío (o el log, si usa el backend de consola de Django para la demo) y el campo marcado. Lo corre una segunda vez, mostrando que no se reenvía.

## Laboratorio

Con guía: agregar la entrada de `cron` para correr el comando una vez al día.

## Ejercicio

Sin guía: simular un fallo de envío (por ejemplo, apuntando a una configuración de SMTP inválida) para un turno entre varios, y confirmar que los demás igual reciben su recordatorio, y que el fallo queda registrado, no silencioso.

## Challenge

Explicá por qué el patrón de "no marcar como enviado hasta confirmar éxito" ya te da reintento automático sin escribir lógica de reintento explícita — es una propiedad del diseño, no un accidente. Identificá si hay algún caso límite donde esto podría enviar un recordatorio duplicado (pista: ¿qué pasa si el email se envía pero el `save()` posterior falla?).

## Project Task

1. Comando de gestión funcional, con manejo de fallos por turno individual.
2. Entrada de `cron` configurada y corriendo.
3. Prueba real de un fallo simulado, confirmando que no bloquea al resto.
4. Commit: `Implementar recordatorios de turno como proceso en segundo plano`.

## Evidencia — Definition of Done

- [ ] Los recordatorios se envían automáticamente, sin intervención manual.
- [ ] Correr el comando dos veces no duplica ningún envío.
- [ ] Un fallo simulado en un turno no impide que los demás reciban su recordatorio.
- [ ] El fallo queda registrado (no silencioso) — conecta directo con la próxima clase.

## Nota sobre abstracción

El patrón (separar lo síncrono de lo asíncrono, usar un flag de estado para lograr idempotencia y reintento) es universal en sistemas que envían notificaciones o procesan trabajo diferido, en cualquier lenguaje. La herramienta concreta —un comando por cron en vez de una cola de mensajes— es una decisión de escala, no de lenguaje.
