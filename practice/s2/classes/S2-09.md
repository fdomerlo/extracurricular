# S2-09 — Testing de integración contra PostgreSQL real

## Contexto

En `S1-06` aprendiste a escribir tests unitarios con `pytest`. Esos tests eran extraordinariamente rápidos y limpios porque el dominio residía en memoria pura: ninguna prueba tocaba el disco, ni la red, ni un motor de base de datos.

En el Semestre 2, sin embargo, la persistencia es parte crítica del sistema. Un test unitario con mocks no puede verificar si una restricción `CHECK (hora_inicio < hora_fin)` funciona, si una clave foránea rechaza un borrado con `ON DELETE RESTRICT`, o si un índice compuesto responde en tiempo y forma.

Esta clase establece el competency gate principal de **`C14 — Tests de integración` (L3)**. Aprenderás a configurar una suite automatizada con `pytest-django` que ejecute pruebas contra una base de datos **PostgreSQL real**, garantizando aislamiento atómico entre tests mediante transacciones reversibles (*rollback*) y comprobando que el código de aplicación interactúa de forma impecable con el motor relacional.

---

## Concepto mínimo

**1. El antipatrón de testear con SQLite si producís con PostgreSQL.**  
Durante años fue común usar SQLite en memoria para tests por velocidad y PostgreSQL en producción. Hoy esto es un grave error de ingeniería:
- SQLite no valida tipos de datos de forma estricta (acepta strings en enteros).
- No soporta concurrencia transaccional real ni tipos nativos como `UUID`, `JSONB` o rangos temporales (`tsrange`).
- Una suite verde en SQLite puede romperse catastróficamente al desplegar en PostgreSQL.  
*Regla de Extracurricular:* **Los tests de integración corren contra el mismo motor que corre en producción.**

**2. Aislamiento y Velocidad con Transacciones de Prueba.**  
Crear y destruir tablas en cada test es lento. `pytest-django` resuelve el dilema mediante el marcador `@pytest.mark.django_db`:
- Antes de cada test, inicia una transacción (`BEGIN`).
- El test ejecuta inserciones, lecturas y modificaciones reales contra PostgreSQL.
- Al finalizar el test, emite un `ROLLBACK`, dejando la base en su estado prístino para el siguiente test en milisegundos.

**3. Fixtures de integración.**  
A diferencia de los fixtures unitarios simples de S1, en integración se diseñan fábricas o fixtures reproducibles que persisten estados válidos del consultorio (ej. un profesional dado de alta, una práctica habilitada y un paciente registrado).

**4. ¿Qué se prueba en un test de integración?**  
- **Persistencia y recuperación fiel:** Lo que se guarda en el modelo debe recuperarse con los tipos exactos (un UUID como objeto `UUID`, un timestamp con zona horaria).
- **Cumplimiento de restricciones del motor:** Intentar persistir un turno solapado o con horario invertido debe levantar una excepción de base de datos (`IntegrityError`).
- **Comportamiento ante borrados (`ON DELETE`):** Intentar borrar un paciente con turnos asociados debe ser bloqueado por PostgreSQL.

## Ejemplo trabajado conceptual

Observá cómo se estructura un test de integración con `pytest` y PostgreSQL:

```python
import pytest
from datetime import date, time
from django.db import IntegrityError
from agenda.models import PacienteModel, ProfesionalModel, PracticaModel, TurnoModel

@pytest.mark.django_db
def test_no_permite_guardar_turno_con_horario_invertido():
    paciente = PacienteModel.objects.create(
        dni="12345678", nombre="Juan", apellido="Perez"
    )
    profesional = ProfesionalModel.objects.create(
        nombre="Dra. Lopez", especialidad="Ortodoncia", matricula="MN100"
    )
    practica = PracticaModel.objects.create(
        nombre="Consulta", duracion_minutos=30
    )

    # El turno tiene hora_inicio (11:00) posterior a hora_fin (10:00)
    with pytest.raises(IntegrityError):
        TurnoModel.objects.create(
            paciente=paciente,
            profesional=profesional,
            practica=practica,
            fecha=date(2026, 11, 20),
            hora_inicio=time(11, 0),
            hora_fin=time(10, 0),
        )
```

## Laboratorio

1. **Instalar dependencias de testing de integración:**  
   ```bash
   uv add --dev pytest-django
   ```
2. **Configurar `pytest.ini`:**  
   En la raíz del proyecto, configurá los settings de Django para pytest:
   ```ini
   [pytest]
   DJANGO_SETTINGS_MODULE = consultorio_project.settings
   python_files = test_*.py
   addopts = --reuse-db
   ```
3. **Ejecutar la suite contra la base de datos local:**  
   Corré pytest apuntando a tu PostgreSQL local (Docker):
   ```bash
   uv run pytest -v
   ```
   Django creará automáticamente una base de prueba (ej. `test_consultorio_db`) y aplicará todas las migraciones desde cero.
4. **Verificar el reuso de la base (`--reuse-db`):**  
   Corré los tests por segunda vez. Notá que la ejecución tarda una fracción de segundo porque no reconstruye las tablas si no hay migraciones nuevas.

## Ejercicio

Creá la suite `tests/test_integration_consultorio.py` con las siguientes pruebas:

1. **Test 1 — Ciclo de vida completo del turno:**  
   Persistir un paciente, profesional y práctica; agendar un turno; consultar la agenda con `select_related` y verificar que todos los datos coincidan.
2. **Test 2 — Violación de unicidad de DNI:**  
   Intentar registrar dos pacientes con el mismo número de documento. Verificar que la base de datos arroje `IntegrityError` y no se guarde el duplicado.
3. **Test 3 — Bloqueo de borrado con turnos activos (`ON DELETE RESTRICT`):**  
   Crear un paciente con un turno agendado. Intentar ejecutar `paciente.delete()`. Verificar que PostgreSQL aborte la operación con `ProtectedError` (o `IntegrityError`), impidiendo que el turno quede huérfano.
4. **Test 4 — Registro de cancelación:**  
   Cancelar un turno creando su registro en `CancelacionTurnoModel` y verificar que el turno permanezca pero su relación con la cancelación sea accesible.

## Nota sobre abstracción

La separación entre tests unitarios puros (sin dependencias externas, rápidos y aislados) y tests de integración (con dependencias de infraestructura como bases de datos o colas) es la base de la Pirámide de Testing. Ambos tipos de tests son indispensables: los unitarios prueban lógica y combinatorias; los de integración prueban contratos y comportamiento real de infraestructura.
