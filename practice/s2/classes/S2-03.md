# S2-03 — Índices y planes de ejecución: EXPLAIN ANALYZE

## Contexto

Las consultas de `S2-02` se ejecutan instantáneamente porque la base de desarrollo apenas contiene una decena de filas de prueba. Sin embargo, en un consultorio real con varios años de actividad, la tabla `turno` acumulará decenas o cientos de miles de registros. En ese escenario, una consulta que filtre por fecha o por profesional sin la estructura adecuada puede degradarse drásticamente.

La optimización de bases de datos no se basa en conjeturas ni en "poner índices a todas las columnas". Se fundamenta en **el análisis científico del plan de ejecución** que el planificador de costos de PostgreSQL diseña para cada consulta. En esta clase aprenderás a utilizar `EXPLAIN` y `EXPLAIN ANALYZE` para diagnosticar el costo de ejecución, entender la diferencia entre escaneos secuenciales y búsquedas por índice, y diseñar índices compuestos con criterio profesional.

---

## Concepto mínimo

**1. `EXPLAIN` vs. `EXPLAIN ANALYZE`.**  
- `EXPLAIN <consulta>`: Muestra el plan estimado por el optimizador (costo computacional arbitrario, filas estimadas, ancho promedio de fila) sin ejecutar la consulta en la base de datos.
- `EXPLAIN ANALYZE <consulta>`: **Ejecuta la consulta en tiempo real** y mide los tiempos efectivos (en milisegundos), comparando las estimaciones del optimizador contra la realidad (*actual time*, *actual rows*, *loops*).  
  *Advertencia de seguridad:* Si ejecutás `EXPLAIN ANALYZE DELETE ...`, los registros se borrarán realmente.

**2. Sequential Scan (`Seq Scan`) frente a Index Scan.**  
- `Seq Scan`: El motor lee secuencialmente todas las páginas de disco de la tabla, una por una. Es altamente eficiente en tablas pequeñas o cuando la consulta debe retornar una porción masiva de la tabla (ej. más del 20-30% de las filas).
- `Index Scan`: El motor recorre la estructura de árbol B (`B-Tree`) del índice para localizar directamente los punteros a disco (`TID`) de las filas que coinciden con el filtro.
- `Bitmap Index Scan`: Técnica intermedia que recopila punteros en un mapa de bits en memoria antes de leer las páginas de datos, ideal para combinar múltiples índices o condiciones.

**3. Selectividad y Costo del Índice.**  
Un índice acelera las lecturas en columnas con **alta selectividad** (donde pocas filas coinciden con cada valor de búsqueda, como un DNI o un `UUID`). En cambio, en columnas con baja selectividad (como un booleano `es_sobreturno`), un índice rara vez será utilizado por el motor. Además, cada índice adicional introduce una penalización en cada operación de escritura (`INSERT`, `UPDATE`, `DELETE`), ya que el motor debe actualizar el árbol B correspondiente.

**4. Índices Compuestos y Orden de Columnas.**  
Un índice sobre `(profesional_id, fecha)` permite acelerar consultas que filtren por `profesional_id`, o por `profesional_id AND fecha`. Sin embargo, no sirve para consultas que filtren únicamente por `fecha`. La regla de oro es ubicar primero la columna con mayor selectividad o que aparezca en condiciones de igualdad estricta.

## Ejemplo trabajado conceptual

Observá la salida simplificada de un plan de ejecución:

```sql
EXPLAIN ANALYZE 
SELECT * FROM paciente WHERE dni = '35123456';
```

Salida típica antes del índice:
```text
Seq Scan on paciente  (cost=0.00..18.50 rows=1 width=72) (actual time=0.042..0.085 rows=1 loops=1)
  Filter: (dni = '35123456'::text)
  Rows Removed by Filter: 499
Planning Time: 0.110 ms
Execution Time: 0.105 ms
```

Tras crear el índice único:
```sql
CREATE UNIQUE INDEX idx_paciente_dni ON paciente(dni);
```

Salida posterior:
```text
Index Scan using idx_paciente_dni on paciente  (cost=0.15..8.17 rows=1 width=72) (actual time=0.015..0.017 rows=1 loops=1)
  Index Cond: (dni = '35123456'::text)
Planning Time: 0.082 ms
Execution Time: 0.030 ms
```

## Laboratorio

1. **Generar volumen de datos con `generate_series()`:**  
   Para observar el comportamiento real de los índices, insertá 20.000 turnos sintéticos en tu base local:
   ```sql
   INSERT INTO turno (id, paciente_id, profesional_id, practica_id, fecha, hora_inicio, hora_fin, es_sobreturno)
   SELECT 
       gen_random_uuid(),
       (SELECT id FROM paciente ORDER BY RANDOM() LIMIT 1),
       (SELECT id FROM profesional ORDER BY RANDOM() LIMIT 1),
       (SELECT id FROM practica ORDER BY RANDOM() LIMIT 1),
       CURRENT_DATE - (RANDOM() * 365)::INTEGER,
       TIME '08:00' + ((RANDOM() * 10)::INTEGER * INTERVAL '1 hour'),
       TIME '08:30' + ((RANDOM() * 10)::INTEGER * INTERVAL '1 hour'),
       FALSE
   FROM generate_series(1, 20000);
   ```
2. **Inspeccionar consulta sin índice:**  
   Ejecutá `EXPLAIN ANALYZE` filtrando por fecha:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM turno WHERE fecha = CURRENT_DATE;
   ```
   Anotá el tiempo de ejecución y el tipo de escaneo (`Seq Scan`).
3. **Crear el índice y comparar:**  
   ```sql
   CREATE INDEX idx_turno_fecha ON turno(fecha);
   EXPLAIN ANALYZE SELECT * FROM turno WHERE fecha = CURRENT_DATE;
   ```
   Observá la transición a `Bitmap Heap Scan` o `Index Scan` y la reducción del tiempo de ejecución.

## Nota sobre abstracción

Los árboles B (`B-Tree`) y los algoritmos de escaneo por mapa de bits son implementados de forma similar en la mayoría de los motores relacionales (Oracle, SQL Server, MySQL InnoDB). Saber leer un árbol de nodos de ejecución es una competencia de ingeniería que trasciende a PostgreSQL y te acompañará en cualquier backend profesional.
