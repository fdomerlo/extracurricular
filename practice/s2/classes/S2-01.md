# S2-01 — Modelo relacional aplicado: diseño del esquema del consultorio

## Contexto

`Paciente`, `Profesional`, `Practica` y `Turno` existen hoy solo en memoria, como objetos Python que desaparecen cuando cerrás el programa. Esta clase los convierte en tablas reales, con las restricciones que la base de datos va a hacer cumplir aunque el código de aplicación tenga un bug. No es releer teoría de bases de datos — es la traducción concreta de un dominio ya diseñado a un esquema real.

## Concepto mínimo

**Una tabla por entidad.** `Paciente`, `Profesional` y `Turno` (entidades de `S1-04`, con identidad propia) se traducen directo a tablas con clave primaria. `Practica`, aunque es un valor en el dominio, también necesita su propia tabla acá: varios turnos la referencian, y una tabla es la forma natural de representar "un catálogo compartido de prácticas" en SQL.

**`Horario` no siempre necesita su propia tabla.** Es un valor chico, atado 1 a 1 a un `Turno` — se representa mejor como columnas directas en la tabla `turno` (`hora_inicio`, `hora_fin`) que como una tabla separada con su propia clave foránea. Crear una tabla para todo lo que es una clase en Python es un error común — la pregunta correcta es si ese valor se comparte o se consulta independientemente, no si tiene su propia clase.

**Las restricciones son la primera línea de defensa, no la única.** `S1-05` ya valida las reglas de negocio en Python. Acá se agregan restricciones equivalentes a nivel de base de datos (`NOT NULL`, `FOREIGN KEY`, `CHECK`) — no porque el código de S1 esté mal, sino porque cualquier inserción que no pase por ese código (una migración de datos, una consulta manual, un bug futuro) va a tener que respetar igual las reglas mínimas. Es redundancia deliberada, no desconfianza en el trabajo anterior.

**Claves primarias.** Se usa `UUID` como en el dominio de `S1-04`, no autoincremental — así el id que genera el dominio en memoria puede ser el mismo que termina en la base, sin tener que esperar a un `INSERT` para saber la identidad de un objeto.

## Demostración

El mentor escribe en vivo, en `psql`, sin ORM:

```sql
CREATE TABLE profesional (
    id UUID PRIMARY KEY,
    nombre TEXT NOT NULL,
    especialidad TEXT NOT NULL
);

CREATE TABLE practica (
    id UUID PRIMARY KEY,
    nombre TEXT NOT NULL,
    duracion_minutos INTEGER NOT NULL CHECK (duracion_minutos > 0)
);

CREATE TABLE paciente (
    id UUID PRIMARY KEY,
    dni TEXT NOT NULL UNIQUE,
    nombre TEXT NOT NULL,
    apellido TEXT NOT NULL,
    telefono TEXT
);

CREATE TABLE turno (
    id UUID PRIMARY KEY,
    paciente_id UUID NOT NULL REFERENCES paciente(id),
    profesional_id UUID NOT NULL REFERENCES profesional(id),
    practica_id UUID NOT NULL REFERENCES practica(id),
    hora_inicio TIME NOT NULL,
    hora_fin TIME NOT NULL,
    fecha DATE NOT NULL,
    CHECK (hora_inicio < hora_fin)
);
```

Notá el `CHECK (hora_inicio < hora_fin)` — es la misma regla que `HorarioInvalidoError` valida en `S1-02`/`S1-03`, ahora también como restricción de base de datos.

## Laboratorio

Con guía: crear la tabla `feriado` (fecha, descripción), decidiendo entre el mentor y el estudiante qué restricciones tiene sentido agregar (¿la fecha puede repetirse? ¿por qué sí o por qué no debería tener un `UNIQUE`?).

## Ejercicio

Sin guía: diseñar cómo registrar cancelaciones tardías (la regla de `S1-05`). Decisión de diseño real: ¿es una columna en `turno` (`cancelado_tardiamente BOOLEAN`) o una tabla separada (`cancelacion` con fecha, motivo, referencia al turno)? Justificá tu elección por escrito antes de crear la tabla.

## Challenge

Agregá un `CHECK` que replique, a nivel de base de datos, alguna otra regla de `S1-05` que todavía no esté cubierta (por ejemplo, que `duracion_minutos` de una práctica sea razonable, o algo específico del dominio que identifiques vos). Documentá en un comentario por qué esa regla merece estar también acá, y no solo en Python.

## Project Task

1. Escribir `schema.sql` con el `CREATE TABLE` de las cuatro tablas principales más `feriado` y la tabla/columna de cancelación tardía del Ejercicio.
2. Crear la base de datos localmente y correr `schema.sql` contra ella desde cero, verificando que no tira errores.
3. Commit: `Definir esquema relacional del consultorio`.

## Evidencia — Definition of Done

- [ ] `schema.sql` corre sin errores contra una base vacía.
- [ ] Cada tabla tiene su clave primaria como `UUID`.
- [ ] Todas las relaciones tienen su `FOREIGN KEY` correspondiente.
- [ ] Al menos un `CHECK` replica una regla de negocio real de `S1-05`.
- [ ] Podés explicar, para cada tabla, por qué existe como tabla separada (o por qué no, en el caso de `Horario`).

## Nota sobre abstracción

El modelo relacional y sus restricciones (claves, `CHECK`, `NOT NULL`) son estándar SQL, no específicos de PostgreSQL — la sintaxis exacta varía levemente entre motores (MySQL, SQLite, SQL Server), pero el diseño es transferible casi sin cambios.
