# S2-01 — Modelo relacional aplicado: Esquema DDL y restricciones de integridad

## Contexto

En el Semestre 1 modelaste el dominio del consultorio exclusivamente en memoria: `Paciente`, `Profesional`, `Practica` y `Turno` existen hoy como dataclasses de Python que desaparecen al cerrar el proceso. 

El objetivo del Semestre 2 es dotar a este sistema de persistencia confiable. Antes de introducir librerías de mapeo objeto-relacional (ORM), el principio rector del programa exige dominar el fundamento: **traducir el dominio a un esquema relacional formal mediante sentencias DDL (Data Definition Language) de SQL**, implementando en el propio motor de base de datos las restricciones que garanticen la integridad de los datos ante cualquier fallo de la aplicación.

No se trata de repetir teoría de normalización académica (1NF/2NF/3NF), sino de diseñar un esquema relacional robusto, auditable y mantenible.

---

## Concepto mínimo

**1. Entidad frente a Tabla.**  
Las entidades de dominio con identidad independiente (`Paciente`, `Profesional`, `Turno`) se mapean directamente a tablas con clave primaria. El catálogo de `Practica`, aunque en memoria se utilizaba como un objeto compartido, requiere su propia tabla relacional para que los turnos puedan referenciarlo formalmente.

**2. Claves primarias UUID vs. Autoincrementales.**  
En S1 se adoptaron identificadores únicos `UUID`. Mantener `UUID` como clave primaria en PostgreSQL (`id UUID PRIMARY KEY`) permite que el dominio continúe generando identidades válidas en memoria antes de persistir el objeto, sin necesidad de esperar un `INSERT` para obtener el ID de la base de datos.

**3. Valores aplanados vs. Tablas separadas.**  
Un error frecuente de diseño consiste en crear una tabla para cada clase de Python. `Horario` en S1 era un *Value Object* pequeño acoplado 1 a 1 al turno. En el modelo relacional no justifica una tabla con su propia clave foránea: se representa de forma natural y eficiente aplanando sus atributos como columnas directas en la tabla `turno` (`hora_inicio TIME`, `hora_fin TIME`).

**4. Restricciones de integridad como primera línea de defensa.**  
El código de Python de S1 valida reglas de negocio con excepciones como `HorarioInvalidoError`. En la base de datos se configuran restricciones equivalentes (`NOT NULL`, `FOREIGN KEY`, `CHECK`, `UNIQUE`):
- Si una migración manual, un script administrativo o un bug en el código intenta insertar datos corruptos, el motor PostgreSQL rechaza la operación a nivel de bloque.
- Esto constituye **redundancia deliberada y defensa en profundidad**, no desconfianza en el código anterior.

---

## Ejemplo trabajado conceptual

Observá cómo se define una tabla relacional aplicando tipos de datos estrictos y restricciones de verificación (`CHECK`) en SQL estándar soportado por PostgreSQL:

```sql
-- Creación de un catálogo auxiliar de consultorios físicos
CREATE TABLE consultorio_sala (
    id UUID PRIMARY KEY,
    numero INTEGER NOT NULL CHECK (numero > 0),
    piso INTEGER NOT NULL DEFAULT 1,
    activa BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT uq_sala_piso_numero UNIQUE (piso, numero)
);
```

Aspectos técnicos destacados:
- `id UUID PRIMARY KEY`: Garantiza unicidad global sin colisiones.
- `CHECK (numero > 0)`: Impide que entren números de sala negativos o cero.
- `UNIQUE (piso, numero)`: Restricción compuesta que evita duplicar números de sala en el mismo piso.

## Laboratorio

Realizá este procedimiento paso a paso en tu terminal:

1. **Levantar el servicio de PostgreSQL:**  
   Iniciá la instancia local mediante Docker Compose o tu instalación de PostgreSQL:
   ```bash
   docker compose up -d db
   ```
2. **Conectarse con el cliente de terminal:**  
   Ingresá a la consola interactiva `psql`:
   ```bash
   docker compose exec db psql -U consultorio -d consultorio_db
   ```
3. **Crear las primeras tablas base:**  
   Ejecutá interactivamente la creación de `profesional` y `practica`:
   ```sql
   CREATE TABLE profesional (
       id UUID PRIMARY KEY,
       nombre TEXT NOT NULL,
       especialidad TEXT NOT NULL
   );

   CREATE TABLE practica (
       id UUID PRIMARY KEY,
       nombre TEXT NOT NULL,
       duracion_minutos INTEGER NOT NULL CHECK (duracion_minutos > 0)
   );
   ```
4. **Verificar la aplicación de restricciones:**  
   Intentá insertar una práctica con duración inválida y observá el error emitido por el motor:
   ```sql
   INSERT INTO practica (id, nombre, duracion_minutos) 
   VALUES (gen_random_uuid(), 'Consulta de prueba', -15);
   ```
   *Debe fallar con:* `ERROR: new row for relation "practica" violates check constraint "practica_duracion_minutos_check"`.

## Ejercicio

Sin mirar soluciones preparadas:

1. Diseñá y escribí la sentencia `CREATE TABLE` para `paciente`:
   - Campos: `id`, `dni`, `nombre`, `apellido`, `telefono`.
   - Considerá qué campo debe poseer restricción `UNIQUE` y cuáles deben ser obligatorios (`NOT NULL`).
2. Diseñá y escribí la sentencia `CREATE TABLE` para `turno`:
   - Claves foráneas hacia `paciente`, `profesional` y `practica` usando `REFERENCES`.
   - Fecha y horario (`hora_inicio`, `hora_fin`).
   - Restricción `CHECK (hora_inicio < hora_fin)` para reflejar la invariante horaria de S1.
3. **Decisión de modelado de cancelaciones tardías:**  
   En `S1-05` se definió la regla de cancelación tardía. Tenés dos alternativas de modelado:
   - *Alternativa A:* Agregar columnas en la tabla `turno` (`cancelado BOOLEAN`, `cancelado_tardiamente BOOLEAN`, `motivo_cancelacion TEXT`).
   - *Alternativa B:* Crear una tabla separada `cancelacion_turno` con clave foránea a `turno`.  
   Redactá una justificación técnica en dos párrafos argumentando cuál opción elegís según la frecuencia esperada de cancelaciones y el principio de normalización.

## Nota sobre abstracción

La sintaxis DDL y las restricciones de integridad (`NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK`) son parte del estándar SQL (`SQL-92` en adelante). Aunque en este semestre utilizamos PostgreSQL como implementación de referencia por su fidelidad a los estándares y robustez en producción, los conceptos aquí aplicados son transferibles sin fricción a MySQL, MariaDB, SQLite u Oracle.
