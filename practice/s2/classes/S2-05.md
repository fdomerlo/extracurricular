# S2-05 — ORM y migraciones: Django sobre el dominio de S1

## Contexto

Esta es la clase donde "SQL a mano antes que el ORM" se cierra: ya sabés escribir el esquema, las consultas, los índices y la protección de concurrencia a mano. De acá en más, Django va a generar buena parte de eso por vos — pero ahora lo vas a poder leer críticamente, no aceptarlo a ciegas.

Importante antes de arrancar: **el trabajo de `S1-04` y `S1-05` no se tira.** El modelado de dominio y las reglas de negocio siguen siendo válidos — lo que cambia es dónde viven los datos, no la lógica que los gobierna.

## Concepto mínimo

**Los modelos de Django reflejan el esquema de `S2-01`, no lo reinventan.** Ya diseñaste las tablas a mano — los modelos son esa misma estructura expresada como clases Python.

```python
from django.db import models
import uuid

class Profesional(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    nombre = models.CharField(max_length=100)
    especialidad = models.CharField(max_length=100)

class Turno(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    paciente = models.ForeignKey("Paciente", on_delete=models.PROTECT)
    profesional = models.ForeignKey(Profesional, on_delete=models.PROTECT)
    practica = models.ForeignKey("Practica", on_delete=models.PROTECT)
    fecha = models.DateField()
    hora_inicio = models.TimeField()
    hora_fin = models.TimeField()
```

**Las migraciones son commits para tu esquema.** `python manage.py makemigrations` genera un archivo Python que describe el cambio; `migrate` lo aplica. Igual que en `S1-07`, cada migración se versiona en git — nunca se edita el esquema a mano en producción sin que quede una migración que lo documente.

**Dónde vive la lógica de negocio ahora.** La regla de solapamiento de `S1-05` no desaparece — se reimplementa contra la base real, típicamente como un método en el modelo o en un manager (`Turno.objects.hay_solapamiento(...)`), que hace una consulta real en vez de recorrer una lista en memoria. La restricción `EXCLUDE` de `S2-04` sigue siendo la protección de fondo; el método de Python es la validación que le da al usuario un mensaje de error entendible antes de que la base rechace el insert.

## Demostración

El mentor crea la app de Django, define los cuatro modelos principales reflejando exactamente el esquema de `S2-01`, corre `makemigrations` y muestra el archivo generado:

```bash
python manage.py makemigrations
cat consultorio/migrations/0001_initial.py
```

Aplica la migración y compara con `psql`:

```bash
python manage.py migrate
psql -d consultorio -c '\d turno'
```

El punto de la comparación: confirmar que lo que generó Django es exactamente lo que se diseñó a mano en `S2-01` — mismos tipos, mismas restricciones, sin sorpresas.

## Laboratorio

Con guía: agregar un campo nuevo a un modelo existente, generar la migración, aplicarla, e inspeccionar el diff del archivo de migración generado.

## Ejercicio

Sin guía: reimplementar la validación de solapamiento de `S1-05` como un método de `Turno` o de su manager, que consulte la base real en vez de una lista en memoria. Escribir al menos un caso de prueba manual (en el shell de Django, `python manage.py shell`) que confirme que detecta un solapamiento real.

## Challenge

Expresá la restricción `EXCLUDE` de `S2-04` de forma declarativa usando `constraints` en la `Meta` del modelo `Turno`, y confirmá que Django la incluye en la migración generada — en vez de tenerla solo en el SQL escrito a mano.

## Project Task

1. App de Django con los cuatro modelos principales, reflejando el esquema de `S2-01` sin desviaciones no justificadas.
2. Primera migración generada y aplicada, commiteada.
3. Validación de solapamiento reimplementada contra la base real.
4. Commit: `Modelos de Django sobre el esquema del consultorio`.

## Evidencia — Definition of Done

## Nota sobre abstracción

Todo ORM (SQLAlchemy en Python, ActiveRecord en Ruby, Entity Framework en .NET) resuelve el mismo problema: mapear objetos a filas de una tabla relacional, y versionar cambios de esquema como migraciones. La sintaxis de Django no es transferible directamente, pero el patrón —modelo, migración, manager— sí lo es.
