# S2-05 — ORM consciente y migraciones desde el dominio

## Contexto

En las cuatro clases anteriores cumpliste con la regla fundacional de Extracurricular: **primero el fundamento, después la abstracción**. Escribiste a mano las sentencias DDL, las restricciones de integridad, las consultas con `JOIN` y agregaciones, los índices con `EXPLAIN ANALYZE` y la resolución de condiciones de carrera mediante transacciones.

Ahora que sabés exactamente qué sucede bajo el capó, es momento de incorporar una herramienta de productividad: el **Object-Relational Mapping (ORM)** y su sistema de migraciones. En esta clase introducimos Django 5.x en el proyecto. Pero no lo usamos como una "caja mágica": tus modelos de Django deben reflejar con precisión quirúrgica el esquema que diseñaste a mano en `S2-01`, y cada migración generada será auditada inspeccionando su código SQL subyacente.

Además, mantenemos el principio de modularidad (`C04`): el dominio en memoria de S1 sigue existiendo; el ORM es una capa de persistencia e infraestructura que traduce entre la base de datos y la lógica del negocio.

---

## Concepto mínimo

**1. ¿Qué es un ORM y por qué usarlo?**  
Un ORM traduce filas relacionales a objetos tipados en el lenguaje de programación, automatizando la serialización de datos y el armado de consultas repetitivas. Su valor no es ocultar SQL, sino:
- Evitar código repetitivo de lectura/escritura de tuplas y mapeo manual.
- Gestionar un historial determinístico y versionado de cambios en el esquema mediante **migraciones**.
- Proteger por defecto contra vulnerabilidades de inyección SQL mediante consultas parametrizadas.

**2. Modelos de Django que replican el esquema real.**  
Los modelos no se inventan desde cero. Traducen la especificación de `S2-01`:
```python
import uuid
from django.db import models

class ProfesionalModel(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    nombre = models.CharField(max_length=200)
    especialidad = models.CharField(max_length=100)
    matricula = models.CharField(max_length=50, unique=True)

    class Meta:
        db_table = "profesional"
```

**3. Migraciones: El historial versionado de la base de datos.**  
Las migraciones son archivos Python versionados en Git que describen transformaciones incrementales del esquema:
- `python manage.py makemigrations`: Inspecciona los modelos y genera un archivo de migración (ej. `0001_initial.py`).
- `python manage.py sqlmigrate <app> <numero>`: **El comando de auditoría fundamental.** Muestra el código SQL exacto que Django ejecutará contra PostgreSQL para esa migración.
- `python manage.py migrate`: Aplica las migraciones pendientes contra la base de datos, registrando su ejecución en la tabla de control `django_migrations`.

**4. Aislamiento del Dominio frente a Modelos de Persistencia.**  
El paquete `consultorio` desarrollado en S1 no debe heredar de `django.db.models.Model`. Tu entidad de dominio `Paciente` sigue siendo una dataclass pura testeable en milisegundos sin base de datos. El modelo `PacienteModel` es un adaptador de persistencia.

## Ejemplo trabajado conceptual

Observá cómo se declara un modelo relacional con restricciones equivalentes a las de SQL:

```python
from django.db import models
from django.db.models import CheckConstraint, Q, F

class PracticaModel(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    nombre = models.CharField(max_length=150, unique=True)
    duracion_minutos = models.PositiveIntegerField()

    class Meta:
        db_table = "practica"
        constraints = [
            CheckConstraint(
                check=Q(duracion_minutos__gt=0),
                name="chk_practica_duracion_positiva"
            )
        ]
```

Al auditar con `sqlmigrate`, se comprueba que Django genera exactamente el `CREATE TABLE practica (...)` con su correspondiente `CHECK (duracion_minutos > 0)`.

## Laboratorio

1. **Incorporar Django al proyecto con `uv`:**  
   Instalá Django y el conector de PostgreSQL:
   ```bash
   uv add django psycopg[binary]
   ```
2. **Inicializar la aplicación Django dentro de la estructura existente:**  
   Configurá un proyecto Django estándar (ej. `consultorio_project`) y una aplicación `agenda` o `persistencia` que mapee las tablas existentes.
3. **Configurar la conexión a PostgreSQL:**  
   En `settings.py`, configurá `DATABASES` apuntando a las variables de entorno de tu base de datos local o Docker:
   ```python
   DATABASES = {
       "default": {
           "ENGINE": "django.db.backends.postgresql",
           "NAME": os.environ.get("DB_NAME", "consultorio_db"),
           "USER": os.environ.get("DB_USER", "consultorio"),
           "PASSWORD": os.environ.get("DB_PASSWORD", "consultorio_pass"),
           "HOST": os.environ.get("DB_HOST", "localhost"),
           "PORT": os.environ.get("DB_PORT", "5432"),
       }
   }
   ```
4. **Auditar la primera migración:**  
   Creá la migración inicial e inspeccionala con `sqlmigrate`:
   ```bash
   python manage.py makemigrations agenda
   python manage.py sqlmigrate agenda 0001
   ```
   *Punto de verificación:* Compará la salida de `sqlmigrate` con tu archivo `schema.sql` de `S2-01`. Debe haber paridad total de tablas, tipos y restricciones.

## Nota sobre abstracción

El patrón Active Record utilizado por Django es uno de los enfoques más difundidos en la industria (similar a Ruby on Rails o Laravel). Otros ecosistemas utilizan Data Mapper (como SQLAlchemy en Python o Hibernate en Java). Ambos buscan el mismo objetivo: sincronizar el estado entre memoria y tablas relacionales manteniendo la trazabilidad mediante migraciones.
