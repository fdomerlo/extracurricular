# S2-08 — Autenticación y permisos por rol (RBAC) en backoffice

## Contexto

Hasta este punto, el acceso al panel de administración se realizó utilizando un superusuario (`is_superuser=True`), que posee facultades irrestrictas para crear, modificar y eliminar cualquier dato. En un entorno real de consultorio médico, esto representa un riesgo inaceptable de seguridad, privacidad y pérdida de datos.

La recepcionista necesita dar de alta pacientes y asignar turnos, pero **bajo ninguna circunstancia debe poder borrar historias clínicas de la base de datos**. Un profesional médico debe poder consultar su agenda del día, pero no alterar la configuración global del sistema ni modificar turnos de colegas sin autorización.

Esta clase introduce el modelo de **Control de Acceso Basado en Roles (RBAC — Role-Based Access Control)** dentro del backoffice de Django. Aprenderás a configurar grupos y permisos granulares (`Group`, `Permission`), a restringir operaciones de borrado y a filtrar la visibilidad de datos según el usuario autenticado.

---

## Concepto mínimo

**1. El subsistema `django.contrib.auth`.**  
Django provee un modelo maduro y auditado para autenticación y autorización:
- `User`: Entidad que representa la identidad del operador (credenciales seguras con hash criptográfico PBKDF2/Argon2, `is_active`, `is_staff`). Para acceder al admin, un usuario debe tener `is_staff = True`.
- `Permission`: Permisos atómicos generados automáticamente por cada modelo registrado: `view`, `add`, `change` y `delete` (ej. `agenda.add_turno`, `agenda.delete_paciente`).
- `Group`: Agrupación lógica de permisos que modela un rol en la organización (ej. rol "Secretaria", rol "Médico").

**2. Principio de Menor Privilegio (Least Privilege).**  
Un usuario solo debe disponer de los permisos estrictamente necesarios para cumplir su función operativa:
- A un operador nunca se le asignan permisos individuales dispersos; se le asigna a uno o más **Grupos**.
- Las acciones destructivas (`delete`) deben denegarse por defecto a los roles operativos ordinarios.

**3. Personalización de permisos en `ModelAdmin`.**  
Podés sobreescribir métodos en la clase de administración para condicionar el comportamiento según el usuario logueado:
- `has_delete_permission(self, request, obj=None)`: Retorna `False` si el usuario no es administrador, eliminando el botón de borrado de la interfaz.
- `get_queryset(self, request)`: Permite particionar la vista de datos (por ejemplo, si el usuario logueado es un profesional médico, solo mostrarle los turnos asignados a su propia persona).

## Ejemplo trabajado conceptual

Sobreescritura de permisos y filtrado por usuario en `ModelAdmin`:

```python
from django.contrib import admin
from .models import TurnoModel

@admin.register(TurnoModel)
class TurnoSeguroAdmin(admin.ModelAdmin):
    list_display = ("fecha", "hora_inicio", "paciente", "profesional")

    def has_delete_permission(self, request, obj=None):
        # Solo los superusuarios pueden borrar turnos físicamente
        return request.user.is_superuser

    def get_queryset(self, request):
        qs = super().get_queryset(request)
        # Si es superusuario o recepcionista, ve todo
        if request.user.is_superuser or request.user.groups.filter(name="Secretaria").exists():
            return qs
        # Si está vinculado a un profesional, ve solo sus turnos
        if hasattr(request.user, "profesional_perfil"):
            return qs.filter(profesional=request.user.profesional_perfil)
        return qs.none()
```

## Ejercicio

1. **Comando de inicialización de roles (RBAC reproducible):**  
   Configurar roles a mano en el admin es frágil y no reproducible. Creá un comando de administración `agenda/management/commands/setup_roles.py` que configure de forma idempotente los grupos y sus permisos:
   - Grupo `Recepcion`: permisos de lectura, creación y modificación de `Paciente` y `Turno`. Cero permisos de eliminación.
   - Grupo `Profesional`: permisos de solo lectura (`view`) sobre `Paciente`, `Turno` y `Practica`.
   - Grupo `Administracion`: permisos completos sobre todos los modelos.
2. Ejecutá el comando desde la terminal:
   ```bash
   python manage.py setup_roles
   ```
3. Verificá que la ejecución repetida del comando sea **idempotente** (no duplique grupos ni arroje errores).

## Nota sobre abstracción

El modelo RBAC (Role-Based Access Control) es el estándar de seguridad adoptado universalmente en sistemas corporativos, desde plataformas cloud (AWS IAM, GCP Cloud IAM) hasta aplicaciones SaaS como Salesforce o Jira. Diseñar roles limpios y desacoplados del código fuente es una competencia fundamental de arquitectura de seguridad.
