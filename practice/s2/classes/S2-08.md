# S2-08 — Autenticación y permisos por rol (mínima)

## Contexto

Hoy cualquiera con acceso al admin puede hacer cualquier cosa con cualquier dato. Eso es aceptable mientras el único usuario sos vos, en desarrollo. No lo es cuando la secretaria y el odontólogo empiecen a usar el sistema con datos reales — cada uno necesita poder hacer solo lo que le corresponde. Esta clase cubre auth mínima, con alcance explícito: **restringe acceso dentro del admin de Django**, no en vistas propias — eso se extiende en `S3`.

## Concepto mínimo

**El modelo de usuario de Django ya existe** — no hace falta diseñarlo desde cero. `User`, con `is_staff` (puede entrar al admin) e `is_superuser` (acceso total sin restricciones).

**Grupos y permisos.** En vez de codear un sistema de roles propio, Django ya tiene `Group` y un sistema de permisos por modelo (`add`, `change`, `delete`, `view`) que se puede asignar por grupo. Crear un grupo "Secretaria" con permisos de `add`/`change` sobre `Turno` pero sin `delete`, y sin ningún permiso sobre `Paciente` si no corresponde, es más robusto que escribir condicionales de "si el usuario es tipo X" desperdigadas por el código.

```python
from django.contrib.auth.models import Group, Permission

grupo_secretaria = Group.objects.create(name="Secretaria")
permisos = Permission.objects.filter(
    content_type__model="turno",
    codename__in=["add_turno", "change_turno", "view_turno"],
)
grupo_secretaria.permissions.set(permisos)
```

**Esto es auth de admin, no de aplicación completa todavía.** El admin de Django respeta estos permisos automáticamente. Cuando en `S3` existan vistas propias, esos mismos permisos se van a poder consultar con `request.user.has_perm(...)` — la base que se arma acá se reutiliza, no se descarta.

## Demostración

El mentor crea el grupo "Secretaria" con permisos limitados sobre `Turno` (sin `delete`, sin acceso a `Paciente` fuera de solo lectura), crea un usuario de prueba en ese grupo, y hace login como ese usuario en el admin — mostrando en vivo que la opción de borrar no aparece, y que `Paciente` aparece pero sin botón de edición.

## Laboratorio

Con guía: crear el grupo "Odontólogo" con permisos más amplios (lectura de todo, edición de `Turno` y `Practica`, sin acceso a borrar pacientes tampoco).

## Ejercicio

Sin guía: crear un usuario de prueba para cada grupo y, sin asumir nada, probar activamente qué puede y qué no puede hacer cada uno en el admin — documentarlo como una tabla corta (rol × acción × permitido/no permitido).

## Challenge

Investigá `request.user.has_perm("app.delete_turno")` en el shell de Django (`python manage.py shell`) para confirmar programáticamente los mismos permisos que probaste a mano en el admin — es una vista previa de cómo se va a usar esto en las vistas propias de `S3`.

## Project Task

1. Grupos "Secretaria" y "Odontólogo" creados con permisos reales, reflejando lo que cada rol necesita hacer en el consultorio (no una aproximación genérica).
2. Dos usuarios de prueba, uno por grupo.
3. `PERMISSIONS.md` con la tabla de rol × acción, verificada probando, no solo diseñada en papel.
4. Commit: `Configurar grupos y permisos por rol`.

## Nota sobre abstracción

Grupos y permisos por rol son un patrón (RBAC — control de acceso basado en roles) presente en cualquier framework serio, con nombres distintos (roles y policies en muchos frameworks de Ruby o Node, por ejemplo). El principio —permisos asignados a un rol, no codeados por usuario individual— es transferible.
