# S2-04 — Transacciones, ACID y concurrencia reproducible

## Contexto

En `S1-05` implementaste la regla de solapamiento: un paciente no puede reservar un turno si el profesional ya está ocupado en ese intervalo. En un programa monopuesto que corre en un único proceso en memoria, esa validación funciona a la perfección.

Sin embargo, en el mundo real, múltiples clientes o secretarias interactúan con el sistema al mismo tiempo. Si dos personas intentan reservar exactamente el mismo horario simultáneamente, ambas pueden consultar la base, ambas leen "horario libre", y ambas insertan su turno. El resultado: **dos turnos superpuestos en la base de datos**. Ninguna validación en Python pudo evitarlo, porque cada proceso actuó sobre una fotografía desactualizada del estado.

Esta clase enseña a utilizar las propiedades ACID de PostgreSQL y a **reproducir deliberadamente una condición de carrera entre dos sesiones concurrentes**, aplicando bloqueos y transacciones para garantizar la consistencia absoluta de los datos.

---

## Concepto mínimo

**1. Atomicidad y Aislamiento (`BEGIN`, `COMMIT`, `ROLLBACK`).**  
Una transacción agrupa múltiples operaciones en una unidad indivisible:
- O se aplican todas con éxito (`COMMIT`), o el sistema revierte todos los cambios al estado previo (`ROLLBACK`) si ocurre cualquier error.
- El nivel de aislamiento por defecto en PostgreSQL es `READ COMMITTED`: una transacción solo ve los cambios que ya fueron confirmados por otras transacciones antes de que comience su propia sentencia actual.

**2. La Condición de Carrera en Concreto.**  
```text
Sesión 1 (Secretaria A)                  Sesión 2 (Secretaria B)
-----------------------                  -----------------------
BEGIN;                                   BEGIN;
SELECT turno de 10:00? (Libre)           
                                         SELECT turno de 10:00? (Libre)
INSERT turno 10:00;                      
COMMIT;                                  
                                         INSERT turno 10:00; -- ¡INCONSISTENCIA!
                                         COMMIT;
```
Ambas transacciones verificaron que no había solapamiento, pero la confirmación tardía de una invalidó el supuesto sobre el cual operó la otra.

**3. Estrategias de Mitigación en el Motor Relacional.**  
- **Bloqueo Pesimista a nivel de fila (`SELECT ... FOR UPDATE`):** La transacción adquiere un cerrojo exclusivo sobre las filas leídas, obligando a cualquier otra transacción concurrente a esperar hasta que se libere el bloqueo con `COMMIT` o `ROLLBACK`.
- **Nivel de Aislamiento `SERIALIZABLE`:** El motor detecta anomalías de serialización (*Serialization Failure*) y aborta automáticamente una de las dos transacciones en conflicto (`ERROR: could not serialize access due to concurrent update`), obligando a la aplicación a reintentar la operación.
- **Restricciones de Exclusión (`EXCLUDE USING gist`):** En PostgreSQL es posible definir una restricción física en el esquema (`tstzrange`) que impida físicamente la inserción de rangos temporales solapados para un mismo profesional, trasladando la garantía al motor a costo cero de aplicación.

## Ejemplo trabajado conceptual

Simulación de transferencia atómica de saldo entre cuentas:

```sql
BEGIN;

-- Bloquear las filas de ambas cuentas para evitar modificaciones concurrentes
SELECT balance FROM cuenta WHERE id = 1 FOR UPDATE;
SELECT balance FROM cuenta WHERE id = 2 FOR UPDATE;

-- Modificar balances
UPDATE cuenta SET balance = balance - 100 WHERE id = 1;
UPDATE cuenta SET balance = balance + 100 WHERE id = 2;

-- Si todo es correcto, consolidar
COMMIT;
```

Si el servidor se reinicia o falla el segundo `UPDATE`, `ROLLBACK` garantiza que la cuenta 1 no pierda su dinero sin que la cuenta 2 lo reciba.

## Laboratorio: Reproducción de la Condición de Carrera

Para este laboratorio necesitarás **dos ventanas de terminal abiertas simultáneamente** conectadas a la misma base de datos.

1. **Preparación (en cualquier terminal):**  
   Asegurate de tener al profesional "Dr. Gómez" cargado en la base de datos.
2. **Terminal A (Sesión 1):**  
   ```sql
   BEGIN;
   -- Verificar disponibilidad
   SELECT COUNT(*) FROM turno 
   WHERE profesional_id = '<uuid-dr-gomez>' 
     AND fecha = '2026-10-15' 
     AND hora_inicio = '10:00';
   -- Devuelve 0 (Libre)
   ```
3. **Terminal B (Sesión 2):**  
   *Sin commitear en la Terminal A*, ejecutá exactamente la misma consulta en la Terminal B:
   ```sql
   BEGIN;
   SELECT COUNT(*) FROM turno 
   WHERE profesional_id = '<uuid-dr-gomez>' 
     AND fecha = '2026-10-15' 
     AND hora_inicio = '10:00';
   -- También devuelve 0 (Libre para la Sesión 2)
   ```
4. **Provocación del conflicto:**  
   - En **Terminal A**, insertá el turno y hacé `COMMIT`:
     ```sql
     INSERT INTO turno (id, paciente_id, profesional_id, practica_id, fecha, hora_inicio, hora_fin)
     VALUES (gen_random_uuid(), '<uuid-paciente-1>', '<uuid-dr-gomez>', '<uuid-practica>', '2026-10-15', '10:00', '10:30');
     COMMIT;
     ```
   - En **Terminal B**, insertá el turno para otro paciente y hacé `COMMIT`:
     ```sql
     INSERT INTO turno (id, paciente_id, profesional_id, practica_id, fecha, hora_inicio, hora_fin)
     VALUES (gen_random_uuid(), '<uuid-paciente-2>', '<uuid-dr-gomez>', '<uuid-practica>', '2026-10-15', '10:00', '10:30');
     COMMIT;
     ```
5. **Verificación del desastre:**  
   Consultá los turnos del Dr. Gómez en esa fecha:
   ```sql
   SELECT id, hora_inicio, hora_fin, paciente_id FROM turno 
   WHERE profesional_id = '<uuid-dr-gomez>' AND fecha = '2026-10-15';
   ```
   *Resultado observable:* Existen dos turnos solapados exactamente a las 10:00. La base de datos aceptó ambos porque ninguna transacción vio la escritura de la otra a tiempo.

## Ejercicio

Resolvé el problema de concurrencia diseñando una solución robusta:

1. **Solución por Bloqueo o Serialización:**  
   Diseñá una transacción con `psql` que prevenga este solapamiento. Podés probar:
   - Opción 1: Bloquear la agenda del profesional para esa fecha (`SELECT id FROM profesional WHERE id = ... FOR UPDATE` o bloqueo de fila de control).
   - Opción 2: Usar nivel de aislamiento `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;`.
2. Repetí el experimento con las dos terminales demostrando que la segunda sesión espera o es abortada con un error de serialización, impidiendo que los dos turnos se guarden juntos.

## Challenge

Investigá el tipo de datos `tsrange` (o `tstzrange`) y la extensión `btree_gist` en PostgreSQL. Diseñá una restricción de exclusión en la tabla `turno`:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE turno ADD CONSTRAINT uq_no_solapamiento 
EXCLUDE USING gist (
    profesional_id WITH =,
    tsrange(fecha + hora_inicio, fecha + hora_fin) WITH &&
);
```
Demostrá que con esta restricción, aun sin transacciones complejas, el motor rechaza instantáneamente cualquier inserción solapada con un error de integridad física.

## Nota sobre abstracción

La concurrencia y las condiciones de carrera existen en cualquier sistema distribuido o cliente-servidor. Resolverlas en la base de datos es el enfoque más seguro porque garantiza consistencia con independencia de cuántos procesos, workers o réplicas de backend estén corriendo en paralelo.
