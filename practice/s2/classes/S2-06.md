# S2-06 — Optimización de consultas con ORM: El problema N+1

## Contexto

El ORM de Django simplifica enormemente la persistencia y la lectura de datos. Sin embargo, esa misma comodidad introduce el defecto de rendimiento más destructivo y extendido del desarrollo de software empresarial: **el problema de las N+1 consultas**.

En código Python, acceder a un atributo relacionado parece una operación trivial en memoria: `turno.paciente.nombre`. Pero si no le indicaste al ORM cómo cargar esa relación de antemano, cada iteración en un bucle disparará una consulta SQL independiente a la base de datos. Si la agenda del día tiene 50 turnos, tu aplicación ejecutará 1 consulta para traer los turnos y 50 consultas individuales adicionales para traer los datos de los pacientes. Lo que en desarrollo con 3 turnos tarda 5 ms, en producción con miles de usuarios colapsa el servidor de base de datos.

En esta clase aprenderás a diagnosticar este problema midiendo la cantidad exacta de consultas emitidas, a solucionarlo usando `select_related` y `prefetch_related`, y a escribir tests automatizados que impidan regresiones de rendimiento.

---

## Concepto mínimo

**1. Anatomía del defecto N+1.**  
Observá este código aparentemente inofensivo:
```python
# Consulta 1: Trae los 100 turnos de la semana
turnos = TurnoModel.objects.filter(fecha__gte="2026-10-01")

for turno in turnos:
    # Consultas 2 a 101: ¡Una consulta individual por cada turno!
    print(f"{turno.hora_inicio}: {turno.paciente.nombre} con {turno.profesional.nombre}")
```
Total de consultas ejecutadas: **1 + 100 + 100 = 201 consultas SQL**. Cada consulta paga el costo de serialización, latencia de red (`round-trip time`) y parseo en PostgreSQL.

**2. `select_related`: Carga inmediata mediante SQL `JOIN`.**  
Para relaciones de cardinalidad simple (`ForeignKey` y `OneToOneField`), `select_related` instruye a Django para que realice un `INNER JOIN` o `LEFT OUTER JOIN` en la misma consulta original:
```python
turnos = TurnoModel.objects.filter(fecha__gte="2026-10-01").select_related(
    "paciente", "profesional", "practica"
)
```
Total de consultas ejecutadas: **1 consulta SQL única**. Toda la información de las 4 tablas viaja en una sola respuesta.

**3. `prefetch_related`: Carga en lote para relaciones N a M o inversas.**  
Para relaciones de múltiples elementos (`ManyToManyField` o relaciones inversas donde una fila tiene muchos hijos), un `JOIN` multiplicaría el volumen de datos devueltos. Django resuelve esto con `prefetch_related`:
1. Ejecuta la consulta principal.
2. Recopila todos los IDs de los objetos obtenidos.
3. Ejecuta una segunda consulta con `WHERE id IN (...)` para traer todos los elementos relacionados de una sola vez.
4. Realiza el emparejamiento en memoria dentro de Python.
Total de consultas: **Exactamente 2 consultas**, sin importar si hay 10 o 10.000 turnos.

**4. Prevención mediante pruebas automatizadas.**  
El rendimiento no se evalúa a ojo. En Django y pytest se utiliza `django_assert_num_queries` o el context manager `capture_queries`:
```python
with django_assert_num_queries(1):
    list(obtener_agenda_completa(fecha))
```
Si un desarrollador futuro introduce accidentalmente un acceso a una relación no cargada, el test falla de inmediato en el pipeline de CI.

## Ejemplo trabajado conceptual

Inspección de consultas SQL en tiempo real con `django.db.connection`:

```python
from django.db import connection, reset_queries

reset_queries()

# Bloque de código bajo prueba
turnos = list(TurnoModel.objects.all()[:10])
for t in turnos:
    _ = t.paciente.nombre

print(f"Total de consultas ejecutadas: {len(connection.queries)}")
# Imprime: Total de consultas ejecutadas: 11 (1 + 10)
```

Al aplicar `select_related("paciente")`:
```python
reset_queries()
turnos = list(TurnoModel.objects.select_related("paciente")[:10])
for t in turnos:
    _ = t.paciente.nombre

print(f"Total de consultas ejecutadas: {len(connection.queries)}")
# Imprime: Total de consultas ejecutadas: 1
```
