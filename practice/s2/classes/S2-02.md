# S2-02 — SQL a mano: consultas sobre el consultorio

## Contexto

Tenés el esquema, pero una base de datos vacía no sirve para nada. Esta clase es la que justifica la regla dura del semestre: todo lo que sigue —el ORM, el admin, las vistas— eventualmente genera SQL por vos. Si no podés escribirlo a mano primero, no vas a poder leer ni confiar en lo que esas capas generan.

## Concepto mínimo

**`JOIN`** combina filas de dos tablas relacionadas. Un `INNER JOIN` solo devuelve filas que tienen correspondencia en ambas tablas; un `LEFT JOIN` devuelve todas las de la izquierda, con `NULL` donde no hay correspondencia — útil para "todos los profesionales, tengan turnos hoy o no".

**`GROUP BY` + agregaciones** (`COUNT`, `SUM`, `AVG`) resumen filas en una sola por grupo. "Turnos por profesional este mes" es un `GROUP BY profesional_id` con `COUNT(*)`.

**Subconsultas y CTEs (`WITH`)** descomponen una consulta compleja en pasos nombrados. Una CTE no es más rápida que una subconsulta equivalente (el motor las optimiza de forma similar) — la diferencia es legibilidad: nombrar un paso intermedio ("turnos_del_dia") es más claro que anidar tres niveles de subconsultas.

## Demostración

El mentor escribe en vivo, contra el esquema de `S2-01` con datos de prueba cargados:

```sql
-- Agenda del día para un profesional
SELECT t.hora_inicio, t.hora_fin, p.nombre AS paciente, pr.nombre AS practica
FROM turno t
JOIN paciente p ON p.id = t.paciente_id
JOIN practica pr ON pr.id = t.practica_id
WHERE t.profesional_id = '...' AND t.fecha = CURRENT_DATE
ORDER BY t.hora_inicio;

-- Turnos por profesional este mes
SELECT profesional_id, COUNT(*) AS total_turnos
FROM turno
WHERE fecha >= date_trunc('month', CURRENT_DATE)
GROUP BY profesional_id;

-- CTE: pacientes con más de dos cancelaciones tardías
WITH cancelaciones_por_paciente AS (
    SELECT paciente_id, COUNT(*) AS total
    FROM cancelacion
    WHERE tardia = true
    GROUP BY paciente_id
)
SELECT p.nombre, c.total
FROM cancelaciones_por_paciente c
JOIN paciente p ON p.id = c.paciente_id
WHERE c.total > 2;
```

## Laboratorio

Con guía: escribir la consulta "todos los profesionales con la cantidad de turnos que tienen hoy, incluidos los que no tienen ninguno" — esto obliga a usar `LEFT JOIN`, no `INNER JOIN`, y es el ejemplo más claro de por qué importa la diferencia.

## Ejercicio

Sin guía: escribir dos consultas — una con `GROUP BY` y una agregación distinta a `COUNT` (por ejemplo, duración promedio de turnos por práctica), y una con CTE (por ejemplo, "próximo turno disponible por profesional", combinando la agenda existente con los horarios de atención de `S1`).

## Challenge

Tomá una de las consultas que ya escribiste con subconsulta anidada y reescribila como CTE, y viceversa con otra. Compará legibilidad, no rendimiento — el punto es entender que son formas distintas de expresar lo mismo.

## Project Task

1. Crear `queries.sql` con al menos 6 consultas reales y útiles para el consultorio: agenda del día, turnos por profesional del mes, pacientes con cancelaciones tardías recurrentes, próximo turno disponible, y dos más que identifiques como necesarias.
2. Cada consulta con un comentario de una línea explicando qué responde.
3. Commit: `Agregar consultas SQL base del consultorio`.

## Nota sobre abstracción

SQL estándar (`JOIN`, `GROUP BY`, CTEs) es prácticamente idéntico entre PostgreSQL, MySQL y SQL Server, con diferencias menores de sintaxis en funciones específicas. Es de las habilidades más directamente transferibles de todo el plan.
