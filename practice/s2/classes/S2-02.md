# S2-02 — SQL a mano: Consultas del dominio, joins y agregaciones

## Contexto

Tenés un esquema relacional con tablas y restricciones de integridad (`schema.sql` de `S2-01`), pero una base de datos vacía no resuelve ningún problema de negocio. Esta clase fundamenta una de las reglas técnicas centrales de Extracurricular: **todo lo que viene más adelante —el ORM, las vistas de administración, los endpoints de consulta— genera consultas SQL por debajo**.

Si no dominás la escritura e interpretación de consultas a mano, no podrás auditar lo que esas herramientas produzcan, ni diagnosticar por qué una consulta es lenta o devuelve datos inesperados. En esta sesión poblamos la base con datos representativos y redactamos las consultas nucleares que el consultorio médico necesita para su operación diaria.

---

## Concepto mínimo

**1. `INNER JOIN` frente a `LEFT JOIN`.**  
- `INNER JOIN` combina filas de dos tablas cuando existe coincidencia en la condición de enlace (`ON`). Si un profesional no tiene turnos asignados hoy, una consulta con `INNER JOIN` entre `profesional` y `turno` lo excluye del resultado.
- `LEFT JOIN` (o `LEFT OUTER JOIN`) preserva todas las filas de la tabla izquierda, rellenando con `NULL` las columnas de la tabla derecha cuando no hay coincidencia. Es indispensable para responder preguntas de negocio como: *"Listar todos los profesionales del consultorio y sus turnos de hoy, mostrando también a quienes tengan la agenda vacía"*.

**2. Agregaciones y `GROUP BY`.**  
Las funciones agregadas (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) colapsan múltiples filas en un único valor resumido. Cuando se combinan con `GROUP BY`, el cálculo se particiona según las columnas indicadas:
- *"Total de turnos atendidos por cada profesional en el mes corriente"*.
- La cláusula `HAVING` filtra grupos calculados (por ejemplo, `HAVING COUNT(*) > 10`), a diferencia de `WHERE` que filtra filas antes de agruparlas.

**3. Common Table Expressions (CTEs con `WITH`).**  
Una CTE (`WITH resumen AS (...) SELECT ... FROM resumen`) descompone una consulta compleja en pasos secuenciales con nombre semántico. A nivel de optimización en PostgreSQL moderno, una CTE se procesa de forma equivalente a una subconsulta, pero su valor reside en la legibilidad y mantenibilidad del razonamiento técnico.

## Ejemplo trabajado conceptual

Observá cómo se estructuran consultas con agregación y CTEs utilizando un esquema genérico de registro de actividad:

```sql
-- Obtener los tres usuarios más activos y su promedio de operaciones
WITH actividad_agrupada AS (
    SELECT 
        usuario_id,
        COUNT(*) AS total_operaciones,
        AVG(tiempo_ms) AS promedio_latencia
    FROM registro_auditoria
    WHERE fecha >= CURRENT_DATE - INTERVAL '30 days'
    GROUP BY usuario_id
    HAVING COUNT(*) >= 5
)
SELECT 
    u.nombre,
    u.email,
    a.total_operaciones,
    ROUND(a.promedio_latencia::numeric, 2) AS latencia_ms
FROM actividad_agrupada a
JOIN usuario u ON u.id = a.usuario_id
ORDER BY a.total_operaciones DESC
LIMIT 3;
```

## Laboratorio

1. **Cargar datos de prueba:**  
   Creá un archivo `seed.sql` con inserciones de prueba:
   - 3 profesionales con distintas especialidades.
   - 3 prácticas médicas (ej. "Consulta General" 30 min, "Limpieza Dental" 45 min, "Extracción" 60 min).
   - 5 pacientes con DNIs y teléfonos válidos.
   - 8 turnos distribuidos entre el día de hoy y la próxima semana, incluyendo al menos un turno cancelado y un sobreturno.
   ```bash
   psql -U consultorio -d consultorio_db -f seed.sql
   ```
2. **Ejecutar la consulta de agenda diaria:**  
   En `psql`, redactá una consulta que liste la agenda de hoy:
   ```sql
   SELECT 
       t.hora_inicio,
       t.hora_fin,
       p.nombre || ' ' || p.apellido AS paciente,
       pr.nombre AS profesional,
       m.nombre AS practica,
       t.es_sobreturno
   FROM turno t
   JOIN paciente p ON p.id = t.paciente_id
   JOIN profesional pr ON pr.id = t.profesional_id
   JOIN practica m ON m.id = t.practica_id
   WHERE t.fecha = CURRENT_DATE
   ORDER BY t.hora_inicio ASC;
   ```
3. **Observar la diferencia con `LEFT JOIN`:**  
   Consultá los profesionales y la cantidad de turnos asignados hoy:
   ```sql
   SELECT 
       pr.nombre,
       COUNT(t.id) AS total_turnos
   FROM profesional pr
   LEFT JOIN turno t ON t.profesional_id = pr.id AND t.fecha = CURRENT_DATE
   GROUP BY pr.id, pr.nombre;
   ```
   *Punto de atención:* Notá por qué se cuenta `COUNT(t.id)` y no `COUNT(*)`. `COUNT(*)` contaría 1 para los profesionales sin turnos debido a la fila con valores `NULL` producida por el `LEFT JOIN`.

## Nota sobre abstracción

La capacidad de articular relaciones entre conjuntos mediante `JOIN` y agregaciones es la esencia del álgebra relacional. Cuando en clases posteriores utilices Django ORM, métodos como `.select_related()`, `.prefetch_related()`, `.annotate()` y `.aggregate()` serán meras traducciones de las sentencias SQL que dominaste en esta sesión.
