# S6-02 — Leer y contribuir a código legacy/ajeno

## Contexto

Es, probablemente, la habilidad más subestimada de toda la carrera: la mayor parte del trabajo real de un desarrollador no es escribir código nuevo sobre una hoja en blanco, es entender código que escribió otra persona —o vos mismo, hace un año— antes de poder cambiarlo con seguridad.

## Concepto mínimo

**Leer código ajeno no es leerlo de arriba abajo.** Se navega desde un punto de entrada concreto: un issue reportado, un comportamiento que querés entender, una función puntual — y desde ahí seguís el hilo (buscar dónde se usa un símbolo, seguir imports, correr el código con un debugger como en `S1-08` para observar el comportamiento real en vez de solo leer y suponer).

**Encontrar dónde contribuir.** Proyectos de código abierto de tamaño moderado suelen etiquetar issues accesibles para quien recién empieza ("good first issue" o equivalente). Documentación desactualizada o poco clara también cuenta como contribución real, y suele ser más accesible que un bug de código.

**El proceso de contribuir tiene su propia etiqueta.** Leer `CONTRIBUTING.md` del proyecto antes de escribir código. Para cambios grandes, abrir un issue primero, antes de invertir tiempo en una solución que tal vez no se acepte. PRs chicos y enfocados se revisan más rápido y se aceptan más fácil que uno grande que toca demasiado a la vez.

**Tu propio código viejo también es "legacy".** El dominio de `S1` tiene ya varios semestres. Mirarlo hoy, con lo que aprendiste desde entonces, es el mismo ejercicio de lectura de código ajeno — aplicado a algo que en su momento escribiste vos.

## Demostración

El mentor elige un proyecto de código abierto real y moderado (idealmente del ecosistema Python/Django, para que sea legible), busca un issue etiquetado como accesible, y traza en vivo el código relevante desde el punto de entrada — usando búsqueda de símbolos y, si hace falta, ejecutando el proyecto con un debugger para confirmar el comportamiento real antes de proponer nada.

## Laboratorio

Con guía: leer juntos un módulo desconocido de ese mismo proyecto, sin tocar nada todavía — solo entender.

## Ejercicio

Sin guía: encontrar un issue real y accesible (o una mejora de documentación) en un proyecto de código abierto relevante para tu stack, entenderlo completo, y preparar una propuesta de solución.

## Challenge

Aplicá el mismo proceso de lectura sistemática al código más viejo de tu propio proyecto (el dominio de `S1`). ¿Qué harías distinto hoy? No hace falta reescribirlo — documentá la reflexión.

## Project Task

Enviar una contribución real (PR, o una mejora de documentación) a un proyecto externo. Este es el primer intento del semestre — la meta completa de `custom-plan.md` (al menos tres contribuciones aceptadas) es un objetivo de todo `S6`, no de esta única clase.

## Evidencia — Definition of Done

- [ ] Entendiste una pieza real de código ajeno lo suficiente como para explicarla.
- [ ] Enviaste al menos una contribución real a un proyecto externo (código o documentación).
- [ ] Aplicaste el mismo proceso de lectura a tu propio código más viejo, con una reflexión documentada.

## Bibliografía de esta clase

No hay bibliografía pre-asignada — el `CONTRIBUTING.md` del proyecto elegido es la referencia relevante en cada caso, y varía según qué proyecto elijas.

## Nota sobre abstracción

Leer código desconocido de forma sistemática es una habilidad completamente transferible entre lenguajes y stacks — de hecho, es una de las pocas habilidades de todo el plan que se vuelve *más* valiosa cuanto más diverso es el código que tuviste que leer.
