# S1-05 — Reglas de negocio del consultorio

## Contexto

Esta es la clase central de todo el semestre. Las entidades de `S1-04` son sustantivos; esta clase les da comportamiento real. Un sistema de turnos que permite reservar dos pacientes en el mismo horario con el mismo profesional no es un sistema de turnos, es una lista con forma de sistema de turnos. Acá es donde el software empieza a valer lo que vale un empleado que conoce el consultorio.

Esto no es teoría abstracta: son las operaciones y restricciones reales del dominio que debés convertir en código verificable y riguroso.

## Concepto mínimo

**Dónde viven las reglas.** Hay dos lugares razonables: como método de la entidad misma (`Turno.se_superpone_con(otro)`), cuando la regla depende solo de los datos de esa entidad; o como una clase de servicio separada (`Agenda`), cuando la regla necesita mirar *varios* turnos a la vez para decidir. Las reglas de esta clase son mayormente del segundo tipo — necesitan conocer todos los turnos existentes de un profesional para decidir si uno nuevo es válido.

**Las cinco reglas que vas a encodear:**

1. **Solapamiento.** Un profesional no puede tener dos turnos que se superpongan en el tiempo. Comparar rangos horarios: dos turnos se superponen si el inicio de uno es anterior al fin del otro, y viceversa — no alcanza con comparar solo las horas de inicio.
2. **Duración variable según práctica.** Cada `Practica` define su propia duración (`S1-04`). El `Turno` no elige una duración libre: la hereda de la práctica al crearse.
3. **Cancelación tardía.** Si se cancela con menos de un umbral de horas de anticipación (definilo con el usuario o stakeholder — es una decisión de negocio real, no técnica), el turno no se borra silenciosamente: queda marcado como cancelación tardía, porque eso tiene consecuencias para el consultorio (un hueco en la agenda que no se pudo reasignar).
4. **Sobreturnos.** A veces el consultorio necesita meter un turno fuera del horario de agenda normal. Esto no es un bug ni una excepción del sistema — es una decisión humana explícita, y el sistema tiene que permitirla sin dejar de dejar registro de que fue un sobreturno, no un turno regular.
5. **Feriados.** El consultorio no atiende ciertos días. Un turno no puede reservarse en una fecha feriada — necesitás una noción de calendario, aunque sea una lista simple por ahora.

**Una regla no encodeada es una regla que no existe.** Si el cliente o stakeholder te describe una regla y no queda plasmada como código verificable con un caso que la prueba, esa regla vive solo en su cabeza — y el sistema la va a violar cuando nadie esté para corregirlo a mano.

## Demostración

Ejemplo trabajado: la primera regla — solapamiento de intervalos — fija el patrón algorítmico y de diseño para las demás:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Horario:
    hora_inicio: str  # formato "HH:MM", validado en __post_init__ (S1-02)
    hora_fin: str

    def se_superpone_con(self, otro: "Horario") -> bool:
        return self.hora_inicio < otro.hora_fin and otro.hora_inicio < self.hora_fin
```

Y el servicio que la usa para decidir sobre un conjunto de turnos existentes:

```python
class Agenda:
    def __init__(self):
        self._turnos: list[Turno] = []

    def puede_reservarse(self, nuevo: Turno) -> bool:
        turnos_del_profesional = [
            t for t in self._turnos if t.profesional == nuevo.profesional
        ]
        return not any(
            t.horario.se_superpone_con(nuevo.horario) for t in turnos_del_profesional
        )

    def reservar(self, nuevo: Turno) -> None:
        if not self.puede_reservarse(nuevo):
            raise TurnoSuperpuestoError(turno_existente=..., turno_nuevo=nuevo)
        self._turnos.append(nuevo)
```

Notá el uso de la comprehension de `S1-02` y la excepción de `S1-03` — esta clase es donde todo lo anterior converge, no contenido aislado.

## Laboratorio

Paso a paso: implementar la regla 2 (duración variable) — el `Turno` no recibe una duración libre al crearse, la deriva de `practica.duracion_minutos` para calcular su `Horario`.

## Ejercicio

Sin guía: implementar las reglas 3 (cancelación tardía) y 5 (feriados). Para feriados, empezá con la estructura más simple que funcione — una lista de fechas — sin sobre-diseñar un calendario completo que todavía no necesitás (principio de incorporación tecnológica: complejidad por necesidad, no por anticipación).

## Challenge

Implementar sobreturnos (regla 4) de forma que quede *explícitamente* distinguido de un turno regular — no un booleano suelto sin contexto, sino algo que cuando alguien lea el código o los datos, entienda inmediatamente que fue una decisión humana deliberada, no el sistema fallando en detectar un solapamiento. Pensalo antes de codearlo: ¿es un campo en `Turno`? ¿Es una subclase? ¿Es un método separado `Agenda.reservar_sobreturno()` que evita la validación de solapamiento a propósito? Cualquiera de las tres puede estar bien — lo que no puede pasar es que sea indistinguible de un bug.
