# S1-09 — Reproducir un bug

## Contexto

Esta clase junta las tres anteriores. Un bug real no llega como "el test `test_solapamiento` falla" — llega como un reporte de un usuario o stakeholder diciendo: "a veces, cuando cancelás un turno con anticipación, el horario no queda libre para otro paciente". Vago, sin pasos exactos, sin garantía de que se repita siempre igual. Convertir eso en algo que podés aislar y reparar con confianza es una habilidad esencial de ingeniería.

## Concepto mínimo

**Un bug que no podés reproducir de forma confiable, no está arreglado aunque "parezca" arreglado.** Si cambiaste algo y el síntoma desapareció, pero no sabés exactamente qué condición lo disparaba, no sabés si lo arreglaste o si dejó de pasar por casualidad.

**El proceso, aplicado a un reporte real y vago:**

1. **Recolectar información.** ¿Qué esperaba que pasara? ¿Qué pasó en cambio? ¿Con qué datos? ¿Siempre, o "a veces"? Un reporte vago casi siempre esconde una condición específica que la persona no identificó como relevante.
2. **Intentar reproducirlo** con datos realistas, no inventados al azar — usá un escenario representativo de lo que reportó el usuario.
3. **Minimizar.** Una vez que lo reproducís, sacá todo lo que no es necesario para que siga pasando. El caso mínimo es más fácil de entender y de convertir en test.
4. **Escribir un test que falle, ANTES de arreglar nada.** Esto es la disciplina central de esta clase: el test rojo es la prueba de que reprodujiste el problema de verdad, no una suposición.
5. **Recién ahí, arreglar** — usando el proceso de `S1-08`.
6. **Verificar que el test pasa a verde**, y que el resto de la suite sigue en verde.

**Por qué el test viene antes del arreglo, no después.** Si escribís el test después de arreglar, no tenés forma de confirmar que el test realmente detecta el bug — podría estar pasando por una razón que no tiene nada que ver. Verlo fallar primero es la única forma de confiar en que, si vuelve a fallar en el futuro, es porque el bug volvió.

## Demostración

Ejemplo trabajado: convertir un reporte verbal vago en un test automatizado en rojo.

**Reporte recibido:**
*"Ayer cancelamos un turno que estaba para dentro de tres días, pero cuando quisimos anotar a otra persona en ese hueco, el sistema siguió diciendo que el horario estaba ocupado."*

1. **Indagación y acotación:**
   - ¿Qué estado quedó registrado? El turno fue cancelado con 72 horas de anticipación (cancelación regular, no tardía).
   - ¿Qué debería pasar? El horario debe quedar disponible para nuevos turnos.
2. **Caso mínimo:**
   - 1 profesional.
   - 1 turno existente de 09:00 a 09:30.
   - Cancelación del turno con anticipación mayor al umbral.
   - Intento de reservar un nuevo turno en ese mismo horario.
3. **Escribir el test que reproduce el fallo (test rojo):**
   ```python
   def test_cancelacion_regular_libera_horario(agenda_con_un_turno):
       # Reproducimos la condición reportada
       turno_original = agenda_con_un_turno._turnos[0]
       agenda_con_un_turno.cancelar(turno_original, anticipacion_horas=72)

       # El sistema debería permitir reservar en el mismo horario
       nuevo_turno = Turno(
           profesional=turno_original.profesional,
           horario=turno_original.horario,
           ...
       )
       assert agenda_con_un_turno.puede_reservarse(nuevo_turno) is True
   ```
4. **Ejecución y confirmación del rojo:**
   Al correr `uv run pytest`, el test falla (`assert False is True`). El bug existe y está atrapado: `puede_reservarse` no estaba ignorando los turnos cancelados al chequear solapamientos.

## Laboratorio

Paso a paso: aislar y escribir el test rojo para el siguiente reporte simulado:

**Reporte:**
*"Quise cargar una práctica de ortodoncia de 45 minutos a las 11:30 y el sistema me dejó avanzar, pero cuando quise reservar el turno siguiente a las 12:15, me dio error diciendo que se solapaba con las 11:30."*

1. Identificá qué datos intervienen: cálculo de hora fin (`11:30 + 45 min = 12:15`) y frontera de solapamiento.
2. Formulá la pregunta de indagación: ¿el operador de solapamiento es inclusivo o excluyente en los extremos?
3. Escribí un test unitario mínimo que plasme este escenario exacto y confirmá que falla antes de implementar cualquier modificación.

## Ejercicio

Sin guía, en una rama nueva (`fix/...`, aplicando `S1-07`): procesar el siguiente reporte vago:

**Reporte:**
*"Cargamos un sobreturno urgente a las 10:00 que duraba 30 minutos. Después quisimos agendar un turno normal a las 10:30 y el sistema lo bloqueó diciendo que el profesional estaba ocupado."*

Realizá el ciclo completo de forma autónoma:
1. Crear rama `fix/sobreturno-libera-agenda`.
2. Escribir el test que reproduce el fallo.
3. Commitear el test en rojo (`git commit -m "test: reproducir bloqueo indebido post-sobreturno"`).
4. Arreglar la causa raíz en el dominio siguiendo los 7 pasos de `S1-08`.
5. Comprobar que el test pasa a verde y la suite completa (`uv run pytest`) pasa sin regresiones.
6. Commitear el arreglo y mergear la rama a `main`.

## Challenge

Si querés explorar técnicas avanzadas, investigá cómo simular datos temporales complejos en tests usando librerías como `time-machine` o `freezegun` para congelar el reloj del sistema y probar cancelaciones dependientes de la hora actual (`datetime.now()`).

## Project Task

Si a esta altura del semestre un usuario real o stakeholder ya probó el sistema y reportó alguna inconsistencia real, tomala como el caso de esta clase con máxima prioridad. Si no hay reportes de usuarios aún, utilizá el caso del Ejercicio:

1. Rama `fix/<descripción-corta>`.
2. Test que reproduce el problema, en rojo, commiteado antes del arreglo.
3. Arreglo, test en verde, suite completa en verde.
4. Merge a `main`.

## Evidencia — Definition of Done

- [ ] El test que reproduce el bug fue commiteado en rojo antes del commit que lo arregla — se puede ver en el historial de git.
- [ ] El caso está minimizado: no tiene datos ni pasos de más que no sean necesarios para disparar el problema.
- [ ] La suite completa está en verde después del arreglo.
- [ ] Podés explicar, con tus palabras, la diferencia entre "el síntoma desapareció" y "el bug está arreglado".
- [ ] El trabajo se hizo en una rama y se mergeó siguiendo el flujo de `S1-07`.

## Nota sobre abstracción

Escribir el test en rojo antes de arreglar es una disciplina de ingeniería de software general (el núcleo de lo que se conoce como TDD aplicado a corrección de bugs), no algo específico de Python ni de pytest. Se aplica igual en cualquier lenguaje con un framework de testing.
