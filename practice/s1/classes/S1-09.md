# S1-09 — Reproducir un bug

## Contexto

Esta clase junta las tres anteriores. Un bug real no llega como "el test `test_solapamiento` falla" — llega como tu papá diciendo "a veces, cuando cancelás un turno justo a último momento, el horario no queda libre para otro paciente". Vago, sin pasos exactos, sin garantía de que se repita siempre igual. Convertir eso en algo que podés arreglar con confianza es una habilidad separada de saber programar.

## Concepto mínimo

**Un bug que no podés reproducir de forma confiable, no está arreglado aunque "parezca" arreglado.** Si cambiaste algo y el síntoma desapareció, pero no sabés exactamente qué condición lo disparaba, no sabés si lo arreglaste o si dejó de pasar por casualidad.

**El proceso, aplicado a un reporte real y vago:**

1. **Recolectar información.** ¿Qué esperaba que pasara? ¿Qué pasó en cambio? ¿Con qué datos? ¿Siempre, o "a veces"? Un reporte vago casi siempre esconde una condición específica que la persona no identificó como relevante.
2. **Intentar reproducirlo** con datos realistas, no inventados al azar — usá algo parecido a lo que tu papá describió.
3. **Minimizar.** Una vez que lo reproducís, sacá todo lo que no es necesario para que siga pasando. El caso mínimo es más fácil de entender y de convertir en test.
4. **Escribir un test que falle, ANTES de arreglar nada.** Esto es la disciplina central de esta clase: el test rojo es la prueba de que reprodujiste el problema de verdad, no una suposición.
5. **Recién ahí, arreglar** — usando el proceso de `S1-08`.
6. **Verificar que el test pasa a verde**, y que el resto de la suite sigue en verde.

**Por qué el test viene antes del arreglo, no después.** Si escribís el test después de arreglar, no tenés forma de confirmar que el test realmente detecta el bug — podría estar pasando por una razón que no tiene nada que ver. Verlo fallar primero es la única forma de confiar en que, si vuelve a fallar en el futuro, es porque el bug volvió.

## Demostración

El mentor da un reporte de bug vago, verbal, sobre el sistema de turnos (por ejemplo: "a veces, si cancelás un turno justo a tiempo, no se libera el horario"). En vivo, sin mirar el código todavía: hace preguntas para acotar el caso ("¿'justo a tiempo' es antes o después del umbral de cancelación tardía?"), arma un intento de reproducción con datos concretos, lo minimiza, y recién ahí escribe el test que falla — mostrando el rojo antes de tocar el código de arreglo.

## Laboratorio

Con guía: el mentor da un segundo reporte vago; juntos siguen el proceso hasta el test rojo (sin arreglar todavía — eso queda para practicar la secuencia completa en el Ejercicio).

## Ejercicio

Sin guía, en una rama nueva (`fix/...`, usando `S1-07`): el mentor da un tercer reporte vago. El estudiante hace el proceso completo solo — reproducir, minimizar, test rojo, arreglar con el proceso de `S1-08`, test verde, suite completa en verde — y mergea la rama al terminar.

## Challenge

Si el bug fuera uno que existe desde hace varios commits (el mentor puede simular esto reintroduciendo un bug antiguo a propósito en una rama descartable), combinar `git bisect run pytest tests/test_del_bug.py` (de `S1-08`) con el test recién escrito para encontrar automáticamente en qué commit se originó.

## Project Task

Si a esta altura del semestre tu papá ya usó el sistema por CLI y tiene algún comentario real (aunque sea chico, aunque no sea técnicamente un "bug" sino algo que no se comporta como esperaba), tomalo como el reporte real de esta clase en vez de uno inventado por el mentor. Si no hay ninguno todavía, usar uno simulado está bien — pero preferí siempre el reporte real cuando exista.

1. Rama `fix/<descripción-corta>`.
2. Test que reproduce el problema, en rojo, commiteado antes del arreglo.
3. Arreglo, test en verde, suite completa en verde.
4. Merge a `main`.

## Evidencia — Definition of Done

- [ ] El test que reproduce el bug fue commiteado en rojo antes del commit que lo arregla — se puede ver en el historial de git.
- [ ] El caso está minimizado: no tiene datos ni pasos de más que no sean necesarios para disparar el problema.
- [ ] La suite completa está en verde después del arreglo.
- [ ] Podés explicar, con tus palabras, la diferencia entre "el síntoma desapareció" y "el bug está arreglado".
- [ ] El trabajo se hizo en una rama y se mergeó siguiendo el flujo de `S1-07`.

## Nota sobre abstracción

Escribir el test en rojo antes de arreglar es una disciplina de ingeniería de software general (el núcleo de lo que se conoce como TDD aplicado a corrección de bugs), no algo específico de Python ni de pytest. Se aplica igual en cualquier lenguaje con un framework de testing.
