# S1-07 — Git en profundidad: ramas y flujo de trabajo

## Contexto

Veniste commiteando directo sobre la rama principal desde `S1-01`. Funciona mientras el proyecto es chico y trabajás solo, en línea recta. Deja de funcionar en el momento en que querés probar algo arriesgado sin romper lo que ya anda, o cuando dos cambios tocan el mismo archivo y necesitás integrarlos sin perder ninguno. Esta clase te da esas dos herramientas.

## Concepto mínimo

**Una rama es un puntero, no una copia.** Crear una rama no duplica el proyecto — es liviano, tan liviano que no hay excusa para no usarlas todo el tiempo que haga falta.

```bash
git switch -c feature/cancelacion-tardia
```

**Merge integra el trabajo de vuelta.** Si la rama principal no cambió mientras trabajabas en la tuya, el merge es *fast-forward* — simplemente mueve el puntero, sin crear un commit nuevo. Si sí cambió, git crea un *merge commit* que junta ambas historias.

**Conflicto de merge.** Pasa cuando la misma línea (o líneas cercanas) del mismo archivo cambió en las dos ramas. Git no adivina cuál versión es la correcta — te lo deja marcado:

```
<<<<<<< HEAD
duracion_minutos: int = 30
=======
duracion_minutos: int = 20
>>>>>>> feature/cancelacion-tardia
```

Resolverlo es editar el archivo a mano hasta que quede como debería quedar (no necesariamente ninguna de las dos versiones tal cual — a veces es una combinación), borrar las marcas `<<<<<<<`, `=======`, `>>>>>>>`, y commitear.

**Mensajes de commit, en serio.** Ya venís escribiendo mensajes desde `S1-01`. La convención que vale la pena adoptar ahora: primera línea corta, en modo imperativo ("Agregar validación de horario", no "Agregué" ni "agregando"), y si el *por qué* no es obvio desde el *qué*, un cuerpo debajo explicándolo.

## Demostración

Ejemplo trabajado: provocación y resolución controlada de un conflicto de merge.

1. Crear una rama y modificar una línea:
```bash
git switch -c demo/conflicto-a
# Modificar por ejemplo la duración por defecto en una clase de práctica
git commit -am "Ajustar duración a 45 minutos"
```

2. Volver a `main` y modificar *la misma línea* con un valor diferente:
```bash
git switch main
# Modificar la misma línea a 40 minutos
git commit -am "Ajustar duración a 40 minutos"
```

3. Intentar integrar la rama:
```bash
git merge demo/conflicto-a
# Salida:
# Auto-merging src/...
# CONFLICT (content): Merge conflict in src/...
# Automatic merge failed; fix conflicts and then commit the result.
```

4. Inspeccionar el estado y resolver:
`git status` muestra el archivo en estado "both modified".
Al abrir el archivo, Git delimitó los cambios conflictivos entre `<<<<<<< HEAD` y `>>>>>>> demo/conflicto-a`.
Se edita manualmente decidiendo la versión final correcta, se eliminan todas las marcas de conflicto, se marca como resuelto con `git add` y se concluye el merge:
```bash
git add src/...
git commit -m "Merge branch 'demo/conflicto-a' resolviendo conflicto de duración"
git log --oneline --graph --all -n 5
```

## Laboratorio

Paso a paso: crear una rama para un cambio chico (agregar un docstring o tipado a una función existente), mergearla de vuelta con fast-forward (sin conflicto), y confirmar en `git log --graph` que la historia avanzó limpiamente en línea recta.

## Ejercicio

Sin guía: crear dos ramas desde el mismo commit base, realizar cambios mutuamente excluyentes sobre la misma línea en cada una, mergear la primera a `main` y luego mergear la segunda para afrontar el conflicto. Resolverlo de forma autónoma y verificar con `git log --graph`.

## Challenge

Investigá `git rebase` como alternativa a merge para mantener un historial lineal en una rama local antes de integrarla. Regla que tenés que poder justificar rigurosamente: nunca hacer rebase sobre commits que ya hayan sido publicados en un repositorio compartido remoto (analizá por qué la reescritura de hashes rompe el trabajo de otros colaboradores).

2. Aplicar ese flujo retroactivamente al menos una vez: elegir un cambio pendiente real del proyecto y hacerlo en una rama.

## Evidencia — Definition of Done

- [ ] Creaste al menos una rama, la mergeaste con fast-forward.
- [ ] Provocaste un conflicto deliberado y lo resolviste de forma autónoma.
- [ ] `git log --graph` del proyecto muestra al menos una rama integrada.
- [ ] `CONVENTIONS.md` documenta el flujo de ramas adoptado.

## Nota sobre abstracción

Git es hoy el estándar de facto de la industria — a diferencia de otras clases de este semestre, acá no hay una "alternativa de stack" real que valga la pena mencionar. El concepto de ramas aisladas e integración posterior existe en cualquier sistema de control de versiones distribuido, pero en la práctica vas a usar git en casi cualquier trabajo.
