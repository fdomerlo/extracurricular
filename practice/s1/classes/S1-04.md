# S1-04 — Modelado de dominio: entidades y valores

## Contexto

Acá modelás `Paciente`, `Profesional`, `Práctica` y `Turno`: las piezas sobre las que se va a construir el resto de los tres años.

## Concepto mínimo

**Entidad vs. valor — la distinción central.** Una **entidad** tiene identidad propia: dos pacientes con el mismo nombre y teléfono siguen siendo dos personas distintas. Un **valor** se define por su contenido: dos objetos `Horario` con los mismos campos son intercambiables, no importa cuál instancia es cuál — ya lo veniste usando en `S1-02` sin nombrarlo así.

Esto tiene una consecuencia concreta en cómo se comparan: una entidad se compara por su identidad (su id), aunque el resto de sus campos cambie con el tiempo (un paciente puede cambiar de teléfono y sigue siendo el mismo paciente); un valor se compara por sus campos (dos horarios son iguales si sus campos son iguales).

**Identidad ≠ dato del mundo real.** El error típico es usar el DNI como identidad. No lo hagas: un DNI puede tener errores de tipeo, puede repetirse por un bug de carga, y en el peor caso puede cambiar (documentos extraviados, trámites). La identidad la genera el sistema — un id propio, no un dato que viene de afuera y que no controlás.

```python
from dataclasses import dataclass, field
from uuid import UUID, uuid4

@dataclass
class Paciente:
    id: UUID = field(default_factory=uuid4)
    dni: str = ""
    nombre: str = ""
    apellido: str = ""
    telefono: str = ""

    def __eq__(self, otro: object) -> bool:
        if not isinstance(otro, Paciente):
            return NotImplemented
        return self.id == otro.id

    def __hash__(self) -> int:
        return hash(self.id)
```

Sobreescribir `__eq__` y `__hash__` es necesario acá porque el comportamiento por defecto de `@dataclass` compara *todos* los campos — que es exactamente lo que querés para un valor, pero no para una entidad.

**Composición por referencia.** `Turno` no duplica los datos de `Paciente` y `Profesional` — los referencia:

```python
@dataclass
class Practica:
    nombre: str
    duracion_minutos: int

@dataclass
class Turno:
    id: UUID
    paciente: Paciente
    profesional: "Profesional"
    practica: Practica
    horario: Horario
```

En memoria (sin base de datos todavía) esto es una referencia directa al objeto. Cuando en `S2` aparezca la persistencia, esa referencia se va a traducir en una clave foránea — pero eso es un problema de la próxima clase, no de esta.

## Demostración

El mentor construye `Paciente` y `Profesional` en vivo, mostrando en modo interactivo el problema que resuelve sobreescribir `__eq__`:

```python
p1 = Paciente(dni="30111222", nombre="Ana", apellido="Gómez")
p2 = Paciente(dni="30111222", nombre="Ana", apellido="Gómez")
print(p1 == p2)  # False — son dos pacientes distintos, aunque los datos coincidan
print(p1 == p1)  # True
```

Y contrastar con `Horario` (valor, de `S1-02`), donde dos instancias con los mismos campos sí son iguales — la diferencia debe quedar visualmente clara en la misma sesión.

## Nota sobre abstracción

La distinción entidad/valor no es de Python — es un concepto de modelado de dominio (proviene de Domain-Driven Design) aplicable en cualquier lenguaje orientado a objetos. Lo que cambia entre lenguajes es la mecánica para implementarlo (en Java sería sobreescribir `equals()`/`hashCode()`, en TypeScript una comparación estructural manual); el criterio de diseño es el mismo en cualquier stack.
