# S1-01 — Entorno de desarrollo

## Contexto

Antes de escribir una sola línea del dominio del consultorio, necesitás algo que hoy se subestima: un entorno que **cualquiera pueda reproducir exactamente**, no solo vos en tu máquina. "Funciona en mi máquina" no es una frase graciosa, es el síntoma de un proyecto que todavía no separó lo que necesita del lugar donde corre.

Esto no es ceremonia. Dentro de un año vas a clonar este mismo repositorio en otra computadora, o tu mentor va a querer correrlo para revisar tu código, o vas a volver después de dos meses sin tocarlo. Si el entorno no es reproducible, perdés horas reconstruyendo algo que debiste resolver una sola vez, hoy.

## Concepto mínimo

**Aislamiento de dependencias.** Un proyecto Python declara qué versión de Python y qué paquetes necesita, y esa declaración vive en un archivo versionado (`pyproject.toml`), no en la cabeza de nadie. Sin esto, "actualicé una librería para otro proyecto" puede romper este sin que te enteres por qué.

**`uv`** es la herramienta que vas a usar para gestionar eso. Reemplaza en un solo comando lo que antes eran tres o cuatro herramientas separadas (`venv`, `pip`, `pip-tools`): crea el entorno virtual, resuelve versiones de dependencias, y las instala. La razón para elegirlo no es moda — es que es determinístico (genera un lockfile) y rápido, lo que importa cuando lo vas a correr docenas de veces por día.

**Estructura del proyecto.** Vas a usar el layout `src/`: el código del paquete vive en `src/consultorio/`, no suelto en la raíz. Esto evita un error clásico de principiante: importar accidentalmente el código desde el directorio de trabajo en vez de desde el paquete instalado, lo que puede ocultar bugs de empaquetado hasta que ya es tarde.

**Control de versiones desde el primer archivo.** No "cuando ya tenga algo andando". Un repositorio sin historial temprano no te deja ver cómo llegaste a donde llegaste — y ese historial es evidencia auditable, no un detalle administrativo.

## Demostración

Esto lo hace el mentor en vivo, explicando cada paso antes de ejecutarlo — no se copia y pega sin mirar.

```bash
# Crear el proyecto
uv init consultorio --package
cd consultorio

# Ver qué generó uv
ls -la
cat pyproject.toml
```

`pyproject.toml` va a tener algo así:

```toml
[project]
name = "consultorio"
version = "0.1.0"
description = "Sistema de gestión de turnos"
requires-python = ">=3.12"
dependencies = []

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

Agregar la dependencia de testing, que vas a usar desde la próxima clase:

```bash
uv add --dev pytest
```

Esto crea (o actualiza) `uv.lock` — el archivo que garantiza que si otra persona corre `uv sync`, obtiene exactamente las mismas versiones que vos. **Este archivo se commitea.** No es un artefacto temporal.

Verificar que el paquete se puede importar:

```bash
uv run python -c "import consultorio; print(consultorio.__file__)"
```

Si esto imprime una ruta dentro de `src/consultorio/`, el layout está bien armado.

Ahora git:

```bash
git init
```

Antes del primer commit, un `.gitignore` mínimo (no exhaustivo — se amplía cuando aparece la necesidad, no antes):

```
.venv/
__pycache__/
*.pyc
.pytest_cache/
```

Nota lo que **no** está ahí: `uv.lock` no se ignora, se versiona.

```bash
git add .
git commit -m "Inicializar proyecto con uv, estructura src/ y pytest"
```

## Laboratorio

Con guía del mentor, pero ejecutando vos:

1. Repetí los pasos de la demostración en tu propia máquina, sin copiar comandos de una lista — escribiéndolos.
2. Abrí `src/consultorio/__init__.py` (uv lo crea vacío) y agregá una constante simple, por ejemplo `__version__ = "0.1.0"`.
3. Confirmá que `uv run python -c "from consultorio import __version__; print(__version__)"` imprime lo que esperás.
4. Hacé un segundo commit separado del primero: `git commit -m "Agregar __version__ al paquete"`.

Si en el paso 3 falla, no le preguntes al mentor de entrada — leé el mensaje de error completo primero. Un `ModuleNotFoundError` en este contexto casi siempre significa que el layout `src/` no quedó bien armado. Diagnosticarlo vos es parte de la clase, no un efecto secundario.

## Ejercicio

Sin guía. En un directorio nuevo, sin mirar la demostración ni tus notas:

- Creá un segundo proyecto descartable (`uv init scratch --package`).
- Agregá una dependencia cualquiera que no sea pytest (por ejemplo `uv add requests`).
- Verificá que el lockfile refleja esa dependencia.
- Inicializá git y hacé al menos dos commits.
- Borrá el `.venv/` a mano y corré `uv sync` — confirmá que se reconstruye solo, exactamente igual.

Esto último es el punto del ejercicio: si podés borrar el entorno virtual y reconstruirlo sin pensar, entendiste el concepto. Si te da miedo borrarlo, todavía no confiás en que es reproducible.

## Challenge

Para quien termine rápido y quiera ir más allá — no es requisito para avanzar:

Agregá un `Makefile` (o script equivalente) con al menos tres comandos: `make test`, `make run`, `make lock`. El objetivo no es la herramienta en sí, es la idea: cualquier persona que clone el repo debería poder ejecutar tareas comunes sin memorizar comandos de `uv`. Documentá esos comandos en un `README.md` de una sola pantalla.

## Project Task

Esto es lo que queda en el proyecto real, no en un descartable:

1. Creá el proyecto definitivo del consultorio con `uv init consultorio --package` (o renombrá el del laboratorio si ya lo armaste sobre el nombre correcto).
2. Estructura mínima esperada:
   ```
   consultorio/
   ├── pyproject.toml
   ├── uv.lock
   ├── .gitignore
   ├── README.md
   ├── src/
   │   └── consultorio/
   │       └── __init__.py
   └── tests/
       └── __init__.py
   ```
3. El `README.md` debe tener, aunque sea en dos líneas: qué es el proyecto, y cómo se levanta (`uv sync`, cómo correr los tests).
4. Primer commit del proyecto real, no del descartable del ejercicio.

Esta estructura es la que vas a usar el resto del semestre — no se vuelve a rehacer en la próxima clase.

## Evidencia — Definition of Done

- [ ] `uv sync` en un clon limpio del repositorio deja el entorno funcional sin pasos manuales adicionales.
- [ ] `git log --oneline` muestra al menos 3 commits atómicos con mensajes que explican qué cambió y, cuando no es obvio, por qué.
- [ ] `uv.lock` está commiteado.
- [ ] `.venv/` y `__pycache__/` **no** aparecen en `git status` después de correr el proyecto.
- [ ] El mentor pudo clonar el repositorio en un directorio nuevo, sin instrucciones fuera del `README.md`, y dejarlo corriendo.
- [ ] Podés explicar la diferencia entre lo que hace `uv add` y lo que hace `uv sync` sin mirar la documentación.

Si algún ítem falla, la clase no está cerrada — no importa cuánto tiempo pasó.

## Nota sobre abstracción

Esta clase usa Python y `uv` en concreto — no es "gestión de dependencias en abstracto". Eso es intencional: la ruta de aprendizaje por defecto de este proyecto es Python + Django + PostgreSQL, y las clases se proyectan desde ese stack, no al revés.

Lo que es transferible, y vale la pena que lo tengas explícito, es el concepto: todo lenguaje serio tiene una forma de declarar dependencias versionadas y aislar el entorno (Node tiene `package.json` + `package-lock.json`, Rust tiene `Cargo.toml` + `Cargo.lock`, Ruby tiene `Gemfile` + `Gemfile.lock` — el patrón se repite porque el problema es el mismo). Si en algún momento trabajás en otro stack, vas a reconocer el problema aunque cambie la herramienta.

Extrapolar esta clase a otro lenguaje o stack no es contenido de este repositorio — es una conversación de mentoría, si y cuando haga falta.
