# S1-02 — Python idiomático

## Contexto

La clase pasada armaste el andamiaje del proyecto. Antes de modelar el dominio del consultorio en serio (eso es la próxima clase), necesitás el vocabulario con el que lo vas a escribir. No es "aprender Python" desde cero — ya sabés programar. Es la diferencia entre código que funciona en Python y código que está escrito *como* Python.

Esa diferencia importa en la práctica: código no idiomático es más largo, esconde bugs típicos (el clásico de argumentos por defecto mutables, más abajo) y es más difícil de leer para cualquiera que ya conozca el lenguaje — incluido vos mismo, dentro de tres meses.

## Concepto mínimo

**Type hints.** Python es dinámico, pero eso no significa que los tipos no existan — significa que no se verifican en tiempo de ejecución por defecto. Anotarlos de todas formas cumple dos funciones: es documentación que no se desactualiza sola (a diferencia de un comentario), y habilita herramientas que detectan errores antes de correr el código. Sintaxis moderna (3.12+):

```python
def turnos_disponibles(fecha: str, profesional_id: int) -> list[str]:
    ...

def buscar_paciente(dni: str) -> Paciente | None:
    ...
```

Nota `list[str]` en vez de `List[str]`, y `Paciente | None` en vez de `Optional[Paciente]` — son la sintaxis actual, la anterior sigue funcionando pero ya es legado.

**Dataclasses.** Resuelven un problema concreto: escribir `__init__`, `__repr__` y `__eq__` a mano para una clase que solo guarda datos es trabajo mecánico y repetitivo, con espacio de sobra para errores de tipeo.

```python
from dataclasses import dataclass

@dataclass
class Horario:
    hora_inicio: str
    hora_fin: str
    duracion_minutos: int
```

Esto te da `__init__`, `__repr__` y `__eq__` gratis. `frozen=True` lo hace inmutable — una vez creado, no se puede reasignar ningún campo. Usalo cuando el objeto representa un valor, no una entidad con identidad propia y estado que cambia (la diferencia entre "valor" y "entidad" la vas a aplicar en serio en la próxima clase).

Un error clásico que las dataclasses evitan si las usás bien:

```python
# MAL — el mismo list se comparte entre todas las instancias
@dataclass
class Agenda:
    turnos: list = []  # esto ni siquiera arranca: Python lo rechaza en runtime

# BIEN
from dataclasses import field

@dataclass
class Agenda:
    turnos: list[str] = field(default_factory=list)
```

Un argumento por defecto mutable (`list`, `dict`, `set` directamente) se evalúa una sola vez, cuando se define la función o clase — no cada vez que se instancia. El resultado es que todas las instancias terminan compartiendo el mismo objeto, y modificar una "contamina" a las demás. `field(default_factory=list)` crea una lista nueva por instancia.

**Comprehensions.** La forma idiomática de transformar o filtrar una colección, en vez de un loop imperativo con `.append()`:

```python
# No idiomático
horarios_manana = []
for h in horarios:
    if h.hora_inicio < "13:00":
        horarios_manana.append(h)

# Idiomático
horarios_manana = [h for h in horarios if h.hora_inicio < "13:00"]
```

Lo mismo existe para diccionarios (`{k: v for ...}`) y sets (`{v for ...}`). Cuando el resultado es grande y no necesitás tenerlo completo en memoria de una, una generator expression (`(x for x in ...)`, sin corchetes) hace lo mismo de forma perezosa.

**Dónde no conviene una comprehension:** cuando tiene más de una condición anidada o más de un `for` anidado. Ahí la comprehension deja de ser más legible que el loop, y "idiomático" pierde sentido si nadie la puede leer de un vistazo.

## Demostración

El mentor muestra en vivo, sobre archivos descartables (no el proyecto real todavía):

```python
# Antes: clase escrita a mano
class HorarioViejo:
    def __init__(self, hora_inicio, hora_fin, duracion_minutos):
        self.hora_inicio = hora_inicio
        self.hora_fin = hora_fin
        self.duracion_minutos = duracion_minutos

    def __repr__(self):
        return f"HorarioViejo({self.hora_inicio!r}, {self.hora_fin!r}, {self.duracion_minutos!r})"

    def __eq__(self, otro):
        return (self.hora_inicio, self.hora_fin, self.duracion_minutos) == \
               (otro.hora_inicio, otro.hora_fin, otro.duracion_minutos)

# Después: la misma clase
from dataclasses import dataclass

@dataclass
class Horario:
    hora_inicio: str
    hora_fin: str
    duracion_minutos: int
```

Correr `python -i` (modo interactivo) y comparar instancias de las dos, mostrando que `Horario(...) == Horario(...)` funciona sin escribir `__eq__`, y `HorarioViejo` también — pero costó 8 líneas más por nada.

Reproducir el bug del argumento mutable en vivo:

```python
@dataclass
class AgendaRota:
    turnos: list = field(default_factory=list)

a1 = AgendaRota()
a2 = AgendaRota()
a1.turnos.append("Turno A")
print(a2.turnos)  # con field(default_factory=list): []
```

Y después sacar el `field(default_factory=list)` para mostrar que sin eso, ni siquiera compila — Python lo bloquea explícitamente para dataclasses (a diferencia de un `__init__` a mano, donde el bug pasa silencioso).

## Nota sobre abstracción

Type hints, dataclasses y comprehensions son sintaxis de Python. El concepto detrás es transferible — casi todo lenguaje moderno tiene alguna forma de esto (TypeScript con interfaces y tipos estructurales, Java con records desde la versión 14, Kotlin con data classes, y transformaciones funcionales de colecciones existen en casi cualquier lenguaje con `map`/`filter` o su equivalente) — pero la sintaxis concreta de cada uno queda fuera de esta clase. Si en algún momento trabajás en otro stack, vas a reconocer el problema que cada una de estas herramientas resuelve, aunque cambie la forma de escribirlo.
