# S1-06 — Testing con pytest aplicado al dominio

## Contexto

En `S1-05` verificaste cada regla de negocio a mano, en modo interactivo. Eso funciona una vez. No funciona la semana que viene, cuando modifiques la regla de cancelación tardía y necesites saber si rompiste el solapamiento sin darte cuenta. Esta clase convierte esas verificaciones manuales en algo que corre solo, en segundos, cada vez que cambiás una línea.

## Concepto mínimo

**Estructura de un proyecto con pytest.** Carpeta `tests/`, archivos `test_*.py`, funciones `test_*`. Pytest los descubre solo — no hace falta registrar nada a mano.

**`pytest.raises` para probar que algo falla como debe.** No alcanza con probar el camino feliz. Si `S1-05` levanta `TurnoSuperpuestoError` ante un solapamiento, necesitás un test que confirme que efectivamente lo levanta — no solo que el caso válido funciona.

```python
import pytest
from consultorio.exceptions import TurnoSuperpuestoError

def test_turno_superpuesto_levanta_error(agenda_con_un_turno):
    with pytest.raises(TurnoSuperpuestoError):
        agenda_con_un_turno.reservar(turno_que_se_superpone)
```

**Fixtures para no repetir setup.** Si cinco tests necesitan un profesional, una práctica y una agenda con un turno ya cargado, ese armado no se copia y pega cinco veces — se declara una vez como fixture y pytest la inyecta donde haga falta.

```python
import pytest

@pytest.fixture
def profesional_dra_lopez():
    return Profesional(nombre="López", especialidad="Odontología general")

@pytest.fixture
def agenda_con_un_turno(profesional_dra_lopez):
    agenda = Agenda()
    agenda.reservar(Turno(profesional=profesional_dra_lopez, horario=Horario("09:00", "09:30"), ...))
    return agenda
```

**`parametrize` para cubrir varios casos sin copiar el test.** La regla de solapamiento tiene varios casos límite reales: se superpone al inicio, se superpone al final, está completamente contenido, es idéntico. Escribir un test por caso a mano es cinco tests casi iguales — `parametrize` lo resuelve con una sola función.

```python
@pytest.mark.parametrize("hora_inicio,hora_fin,se_superpone", [
    ("09:15", "09:45", True),   # se superpone al final del turno existente
    ("08:45", "09:15", True),   # se superpone al inicio
    ("09:00", "09:30", True),   # idéntico
    ("09:30", "10:00", False),  # justo después, no se superpone
    ("08:00", "08:30", False),  # completamente antes
])
def test_solapamiento_casos_limite(hora_inicio, hora_fin, se_superpone):
    h1 = Horario("09:00", "09:30")
    h2 = Horario(hora_inicio, hora_fin)
    assert h1.se_superpone_con(h2) == se_superpone
```

Este es exactamente el tipo de test que vale la pena escribir: cubre los casos límite reales de una regla de negocio real, no un ejemplo de juguete.

## Demostración

El mentor escribe en vivo el test parametrizado de solapamiento de arriba, corriéndolo con `uv run pytest -v` y mostrando cómo el nombre de cada caso aparece individualizado en la salida — eso importa cuando falla uno de cinco y necesitás saber cuál sin leer el código.

Después rompe deliberadamente la regla (invierte una comparación en `se_superpone_con`) para mostrar que el test falla, y lo repara para mostrar que vuelve a pasar — el punto es que el test detectó el problema antes que un humano leyendo el código.

## Ejercicio

Sin guía: escribir tests para las reglas de sobreturno y feriados de `S1-05`, usando `pytest.raises` donde corresponda y al menos una fixture propia.

## Challenge

Investigá la librería `hypothesis` (property-based testing) y escribí, para la regla de solapamiento, un test que en vez de casos fijos genere horarios aleatorios y verifique una propiedad general (por ejemplo: "si dos horarios no se superponen según la función, entonces invertir su orden tampoco cambia el resultado"). No hace falta que quede perfecto — es exploración, no requisito del semestre.

## Project Task

1. Construir la suite completa de `tests/` cubriendo las cinco reglas de `S1-05`, usando fixtures para el setup compartido y al menos un test parametrizado.
2. Configurar pytest en `pyproject.toml` (sección `[tool.pytest.ini_options]`) para que `uv run pytest` corra sin flags adicionales.

## Evidencia — Definition of Done

- [ ] Cada una de las cinco reglas de `S1-05` tiene al menos un test.
- [ ] Los tests corren en menos de 5 segundos (`time uv run pytest`).
- [ ] Hay al menos una fixture reutilizada por más de un test.
- [ ] Hay al menos un test parametrizado cubriendo casos límite reales, no inventados.
- [ ] Hay al menos un test que verifica que una excepción se levanta cuando corresponde (`pytest.raises`).
- [ ] Rompiste una regla a propósito, viste el test fallar, y lo volviste a arreglar — se lo mostraste al mentor en vivo.

## Nota sobre abstracción

Fixtures, parametrización y `assertRaises`/`pytest.raises` son ideas presentes en prácticamente cualquier framework de testing (JUnit, Jest, RSpec) bajo otros nombres. El patrón —setup reutilizable, cobertura de casos límite sin duplicar código, verificación explícita de que los errores ocurren cuando deben— es transferible; la sintaxis de pytest no lo es.
