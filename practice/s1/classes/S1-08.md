# S1-08 — Pensar como debugger

## Contexto

Hasta acá, cuando algo falló, probablemente lo resolviste mirando el código y probando cambios hasta que anduvo. Eso funciona en problemas chicos. No funciona cuando el bug está dos capas más abajo de donde se manifiesta, y cambiar cosas al azar solo agrega ruido a lo que ya es confuso. Esta clase reemplaza "probar cosas a ver si anda" por un proceso.

## Concepto mínimo

**El proceso, en orden, sin saltarse pasos:**

1. **Reproducir.** Si no podés hacer que el bug pase de nuevo, de forma confiable, no podés saber si lo arreglaste. Esto a veces es el paso más largo.
2. **Aislar.** Reducir el caso hasta el mínimo que sigue disparando el problema. Cuanto menos código esté involucrado, más fácil es ver qué está mal.
3. **Formular una hipótesis.** Antes de tocar nada: "creo que el problema es que `horario.hora_fin` se está comparando como string en vez de convertirse a un tipo de hora". Una hipótesis concreta, no "algo está mal por acá".
4. **Probar la hipótesis.** Inspeccionar el estado real en el momento del fallo, no adivinar desde afuera.
5. **Arreglar.** Recién acá se cambia código.
6. **Verificar.** Correr la suite de tests (`S1-06`) — no solo el caso que arreglaste, toda la suite, para confirmar que no rompiste otra cosa.
7. **Prevenir regresión.** Si no había un test que hubiera atrapado este bug, escribilo ahora. Esto es exactamente el tema de la próxima clase.

**Leer un traceback de abajo hacia arriba.** La última línea es *dónde* explotó, no necesariamente *por qué*. La causa raíz suele estar más arriba en la pila, en una llamada anterior que dejó el estado en una condición que la línea final no supo manejar.

**`breakpoint()` en vez de `print()` para cualquier cosa que no sea trivial.** `print()` te obliga a adivinar de antemano qué vas a necesitar ver. `breakpoint()` (built-in desde Python 3.7, no hace falta importar `pdb` a mano) te para ahí mismo y te deja inspeccionar cualquier variable en vivo, tantas veces como necesites, sin volver a correr el programa.

```python
def puede_reservarse(self, nuevo: Turno) -> bool:
    breakpoint()
    turnos_del_profesional = [...]
    ...
```

Comandos mínimos una vez adentro: `n` (siguiente línea), `s` (entrar a la función que se está por llamar), `c` (continuar hasta el próximo breakpoint), `l` (ver el código alrededor), y escribir el nombre de cualquier variable para inspeccionarla.

`print()` sigue teniendo su lugar — para una verificación rápida y puntual. La regla práctica: si necesitás más de dos `print()` para entender un problema, ya deberías estar usando `breakpoint()`.

## Demostración

Ejemplo trabajado: diagnóstico sistemático de un fallo usando `breakpoint()`.

Supongamos que un test de solapamiento falla inesperadamente ante horarios adyacentes:

```python
# En src/consultorio/domain.py
def se_superpone_con(self, otro: "Horario") -> bool:
    return self.hora_inicio <= otro.hora_fin and otro.hora_inicio <= self.hora_fin
```

1. **Reproducir y aislar:** Al correr `uv run pytest tests/test_solapamiento.py`, el caso `"09:30", "10:00"` (que termina justo cuando el otro empieza) falla porque el operador `<=` considera superpuesto un turno que toca el límite exacto.
2. **Inspeccionar con `breakpoint()`:** Insertamos un punto de interrupción en la función:
   ```python
   def se_superpone_con(self, otro: "Horario") -> bool:
       breakpoint()
       return self.hora_inicio <= otro.hora_fin and otro.hora_inicio <= self.hora_fin
   ```
3. **Exploración en sesión interactiva (Pdb):**
   ```text
   > .../domain.py(58)se_superpone_con()
   -> return self.hora_inicio <= otro.hora_fin and otro.hora_inicio <= self.hora_fin
   (Pdb) p self.hora_inicio, self.hora_fin
   ('09:00', '09:30')
   (Pdb) p otro.hora_inicio, otro.hora_fin
   ('09:30', '10:00')
   (Pdb) p self.hora_inicio <= otro.hora_fin
   True
   (Pdb) p otro.hora_inicio <= self.hora_fin
   True  # <-- ¡Acá está el problema! '09:30' <= '09:30' da True cuando deberían ser disjuntos
   (Pdb) c
   ```
4. **Hipótesis y arreglo:** La condición correcta para intervalos abiertos/semiabiertos contiguos es `<` estricto, no `<=`. Modificamos el código a `<`.
5. **Verificación:** Ejecutamos `uv run pytest` y confirmamos que la suite completa pasa en verde.

## Laboratorio

Paso a paso: aislar un error de mutación de estado.

Copia el siguiente fragmento problemático en un script de prueba o rama temporal:

```python
class AgendaConBug:
    def __init__(self, turnos_iniciales=[]):  # mutable default argument
        self._turnos = turnos_iniciales

    def agregar(self, turno):
        self._turnos.append(turno)
```

1. Escribí un test o script que cree dos instancias independientes de `AgendaConBug` y agregue un turno a la primera.
2. Comprobá por qué la segunda agenda también contiene el turno agregado.
3. Usá `breakpoint()` en `__init__` e inspeccioná el `id(self._turnos)` en ambas instancias para verificar la hipótesis del objeto compartido.
4. Corregí el error usando `turnos_iniciales: list[Turno] | None = None` y verificá.

## Ejercicio

Sin guía: Caso de estudio de regresión sutil.

En tu código de `Agenda` (o en una rama `test/debug-exercise`), introducí voluntariamente el siguiente escenario de bug:
"Al calcular si un turno cae en día feriado, la comparación evalúa `nuevo.fecha in self._feriados`, pero `self._feriados` almacena objetos `date` mientras que `nuevo.fecha` fue parseado como string `'YYYY-MM-DD'` (o viceversa)."

Seguí estrictamente los 7 pasos del proceso:
1. Escribí un test que reproduzca el fallo (debe fallar).
2. Insertá `breakpoint()` antes de la evaluación.
3. Inspeccioná los tipos y valores exactos en Pdb (`type(...)`, `p ...`).
4. Formulá por escrito tu hipótesis.
5. Corregí la causa raíz garantizando homogeneidad de tipos.
6. Corré toda la suite de tests.
7. Comprobá que el test de regresión que escribiste previene que el error vuelva a ocurrir.

## Nota sobre abstracción

El proceso (reproducir → aislar → hipótesis → verificar → arreglar → confirmar → prevenir) no depende de Python ni de ningún lenguaje — es la misma disciplina en cualquier stack. Lo específico de Python es la herramienta (`breakpoint()`/`pdb`); otros lenguajes tienen su propio debugger integrado (el debugger de Node, `gdb` para C, el debugger de un IDE para Java) que hace lo mismo con otra sintaxis.
