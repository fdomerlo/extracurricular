# S1-03 — Manejo de errores: excepciones propias del dominio

## Contexto

En el ejercicio de `S1-02` validaste `HorarioAtencion` con un `ValueError` genérico, con la nota explícita de que era provisorio. Esta clase resuelve eso: `ValueError` no dice nada sobre *qué* falló en términos del consultorio — solo que algo, en algún lado, no era válido. Cuando en `S3` tengas que decidir qué mensaje mostrarle a la secretaria si intenta reservar un turno superpuesto, necesitás poder distinguir ese error de, por ejemplo, un DNI mal formado — y no vas a hacerlo parseando texto de un mensaje.

## Concepto mínimo

**Por qué una jerarquía propia.** Una excepción con nombre (`TurnoSuperpuestoError`) es información estructurada: quien la captura puede decidir qué hacer según el *tipo*, no según el contenido del mensaje. Eso es frágil — el día que cambiás el texto del mensaje, rompés cualquier código que lo estuviera parseando.

**Una base común.** Toda excepción propia del dominio hereda de una base (`ConsultorioError`), que a su vez hereda de `Exception`. Esto te da un punto único donde capturar "cualquier error del dominio" sin capturar errores de Python en general (un `KeyError` por un bug tuyo no debería tratarse igual que un turno superpuesto).

```python
class ConsultorioError(Exception):
    """Base para todos los errores del dominio del consultorio."""
```

**Las excepciones cargan datos, no solo texto.** Un mensaje de error que un humano lee es útil, pero si además guardás los datos relevantes como atributos, ese error se vuelve inspeccionable por código, no solo legible.

```python
class HorarioInvalidoError(ConsultorioError):
    def __init__(self, hora_inicio: str, hora_fin: str):
        self.hora_inicio = hora_inicio
        self.hora_fin = hora_fin
        super().__init__(
            f"Horario inválido: inicio {hora_inicio} no es anterior a fin {hora_fin}"
        )
```

**Excepción vs. valor de retorno.** No todo error se levanta como excepción. Si "no encontrado" es un resultado esperado y frecuente (buscar un paciente que puede no existir), a veces conviene devolver `None` y dejar que quien llama decida — levantar una excepción ahí fuerza a todo el código que llama a envolver la llamada en `try/except` aunque el caso "no encontrado" sea completamente normal. La regla práctica: excepción para lo que es un error real del dominio (un horario inválido, un turno superpuesto); `None` o similar para lo que es un resultado válido aunque vacío.

## Demostración

Refactorizar en vivo el `HorarioAtencion` de `S1-02`:

```python
# Antes
def __post_init__(self):
    if self.hora_inicio >= self.hora_fin:
        raise ValueError("hora_inicio debe ser anterior a hora_fin")

# Después
def __post_init__(self):
    if self.hora_inicio >= self.hora_fin:
        raise HorarioInvalidoError(self.hora_inicio, self.hora_fin)
```

Mostrar en modo interactivo cómo capturar selectivamente:

```python
try:
    horario = HorarioAtencion("14:00", "09:00")
except HorarioInvalidoError as e:
    print(f"Falló con horarios: {e.hora_inicio} - {e.hora_fin}")
```

## Nota sobre abstracción

Una jerarquía de excepciones propia del dominio no es una idea específica de Python — es una práctica estándar en cualquier lenguaje con excepciones (Java, C#, Ruby, TypeScript). Lo que cambia es la sintaxis de herencia; el criterio de diseño (una base común, subclases con datos estructurados, excepción vs. valor de retorno) es el mismo en cualquier stack.
