# S3-02 — Django: vistas, plantillas y formularios

## Contexto

Esta es la clase donde alguien fuera de vos empieza a poder tocar el sistema sin pasar por el admin. Todo lo de `S3-01` deja de ser teórico acá: cada vista que escribas es, literalmente, código que decide qué método acepta y qué código de estado devuelve.

## Concepto mínimo

**Vista, URL, plantilla — el triángulo básico.** Una vista es una función que recibe una petición y devuelve una respuesta. `urls.py` mapea una ruta a esa función. Una plantilla separa el HTML de la lógica Python.

```python
# views.py
from django.shortcuts import render
from .models import Turno

def agenda_del_dia(request):
    turnos = Turno.objects.select_related("paciente", "profesional", "practica").filter(fecha=hoy())
    return render(request, "agenda.html", {"turnos": turnos})
```

Notá `select_related` de `S2-06` — esto no es contenido nuevo, es aplicar lo ya aprendido en el lugar donde realmente importa: una vista que se va a ejecutar en cada carga de página.

**Plantillas con herencia.** Un `base.html` con la estructura común, y cada página extiende con `{% extends "base.html" %}` y llena bloques con `{% block contenido %}`. Copiar y pegar el `<head>` en cada template es la señal de que falta esto.

**Formularios no reinventan la validación de `S1-05`.** Un `ModelForm` de Django valida tipos y campos requeridos automáticamente, pero las reglas de negocio (solapamiento, feriados) siguen viviendo donde ya viven — el formulario las invoca, no las duplica.

```python
class TurnoForm(forms.ModelForm):
    class Meta:
        model = Turno
        fields = ["paciente", "profesional", "practica", "fecha", "hora_inicio"]
```

## Challenge

## Nota sobre abstracción

El patrón vista-plantilla (o su equivalente MVC/MVT) existe en casi cualquier framework web server-rendered: Rails, Laravel, Spring MVC. La sintaxis de Django no es transferible, el patrón sí.
