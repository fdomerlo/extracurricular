# S3-10 — Backups automatizados y logs de producción

## Contexto

Esta clase cierra un criterio que viene pendiente desde `S2-01`: un backup que nunca se restauró no es un backup, es una suposición. Con el sistema ya en producción (`S3-09`), este es el momento de dejar de suponer.

## Concepto mínimo

**`pg_dump`** genera una copia de la base en un formato restaurable. Automatizado con `cron` (o un timer de `systemd`), corre solo, sin depender de que alguien se acuerde.

```bash
# crontab -e
0 3 * * * pg_dump -U consultorio_user consultorio | gzip > /backups/consultorio_$(date +\%Y\%m\%d).sql.gz
```

**El backup no sirve si vive en el mismo disco que la base.** Si el disco del servidor falla, se pierden los dos. Como mínimo, copiar los backups a otro lugar (almacenamiento separado, otro servidor, un servicio de almacenamiento en la nube) — no hace falta una solución elaborada, alcanza con que no dependa del mismo disco.

**Restaurar, de verdad, al menos una vez.** No como ejercicio teórico — tomar un backup real, y restaurarlo en un entorno de prueba, confirmando que los datos vuelven correctamente. Esta es la única forma de saber si el proceso de backup sirve para algo.

**Logging de producción, con una regla que no se negocia.** Los logs de la aplicación nunca deben incluir datos de pacientes — ni nombre, ni DNI, ni motivo de consulta. Esto no es una sugerencia de buenas prácticas genérica: es la misma advertencia legal de `custom-plan.md` aplicada al lugar exacto donde más fácil es romperla sin querer (un log de debug que imprime un objeto completo, por ejemplo).

```python
LOGGING = {
    "version": 1,
    "handlers": {"file": {"class": "logging.FileHandler", "filename": "/var/log/consultorio/app.log"}},
    "root": {"handlers": ["file"], "level": "INFO"},
}
```

## Demostración

El mentor configura el cron de backup, y después —en un entorno de prueba, nunca en el real— simula una pérdida total de la base (`DROP DATABASE`) y la restaura en vivo desde el backup, confirmando que los datos vuelven exactamente como estaban.

## Laboratorio

Con guía: configurar el logging básico de Django, distinguiendo nivel `INFO` (operación normal) de `ERROR` (excepciones), y confirmar que ningún log generado incluye datos de pacientes.

## Ejercicio

Sin guía: copiar los backups generados a una ubicación separada del servidor original (puede ser tan simple como copiarlos a otra máquina, o un servicio de almacenamiento gratuito), y restaurar desde esa copia externa —no desde el archivo local— para confirmar que la copia externa es efectivamente usable.

## Challenge

Armá un chequeo simple (un script, o incluso una alerta por email) que avise si el cron de backup no corrió en las últimas 24-48 horas — un backup que dejó de correr silenciosamente es tan malo como no tener ninguno.

## Project Task

1. Backup automatizado corriendo por cron, verificado en ejecuciones reales (no solo configurado).
2. Una restauración real completada desde una copia almacenada fuera del servidor original.
3. Logging de producción configurado, auditado para confirmar que no expone datos de pacientes.
4. Commit: `Automatizar backups y configurar logging de producción sin datos sensibles`.

## Evidencia — Definition of Done

- [ ] El cron de backup corrió automáticamente al menos una vez sin intervención manual.
- [ ] Restauraste una base completa desde un backup guardado fuera del servidor original, y confirmaste que los datos son correctos.
- [ ] Revisaste los logs generados y confirmaste que no contienen ningún dato de paciente.
- [ ] Esto cierra el criterio de `custom-plan.md`: "los backups corren solos y probaste una restauración completa".

## Nota sobre abstracción

Backup automatizado + restauración verificada + logging sin datos sensibles son prácticas operativas universales, sin relación con el stack elegido. La herramienta concreta (`pg_dump`, `cron`) cambia según el motor de base de datos y el sistema operativo; la disciplina no.
