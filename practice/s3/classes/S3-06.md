# S3-06 — Docker para la aplicación

## Contexto

`S1-01` resolvió "funciona en mi máquina" a nivel de dependencias de Python con `uv`. Esta clase lo resuelve a nivel del sistema completo: versión de Python, librerías del sistema operativo, todo lo que hace que un proyecto ande en tu máquina y falle en otra por razones que no tienen nada que ver con tu código.

## Concepto mínimo

**Un `Dockerfile` describe cómo construir una imagen**, paso a paso, desde una base:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev
COPY . .
CMD ["uv", "run", "gunicorn", "consultorio.wsgi", "--bind", "0.0.0.0:8000"]
```

**El orden de las instrucciones importa.** Copiar `pyproject.toml`/`uv.lock` e instalar dependencias *antes* de copiar el resto del código permite que Docker reutilice esa capa (no reinstala todo) si solo cambiaste código de la aplicación, no las dependencias — construir la imagen de nuevo es mucho más rápido.

**`.dockerignore`** evita que archivos innecesarios (o sensibles) terminen dentro de la imagen — el `.venv` local, `__pycache__`, y crucialmente cualquier archivo `.env` con secretos.

## Demostración

El mentor escribe el `Dockerfile`, construye la imagen (`docker build -t consultorio .`), la corre (`docker run -p 8000:8000 consultorio`), y confirma que responde igual que corriendo local con `uv run` — sin que la máquina tenga Python instalado del lado de afuera del contenedor.

## Laboratorio

Con guía: escribir `.dockerignore` revisando qué terminó dentro de la imagen sin necesidad (`docker run --rm consultorio ls -la` para inspeccionar).

## Ejercicio

Sin guía: reordenar el `Dockerfile` si hace falta para maximizar el reuso de capas, y medir con `time docker build` la diferencia entre un build desde cero y un build después de cambiar solo una línea de código de la aplicación (no de dependencias).

## Challenge

Compará el tamaño final de la imagen usando `python:3.12` completo vs `python:3.12-slim`, con `docker images`. Explicá el trade-off: menos tamaño no siempre significa "mejor" sin matices.

## Project Task

1. `Dockerfile` funcional para el proyecto completo.
2. `.dockerignore` revisado, sin secretos ni archivos innecesarios dentro de la imagen.
3. Commit: `Agregar Dockerfile para la aplicación`.

## Evidencia — Definition of Done

- [ ] `docker build` completa sin errores.
- [ ] `docker run` sirve la aplicación correctamente.
- [ ] La imagen no contiene ningún archivo `.env` ni secreto (verificado inspeccionando, no asumido).
- [ ] Podés explicar cada línea del `Dockerfile` sin mirar notas.

## Nota sobre abstracción

Contenerizar una aplicación es independiente del lenguaje — el mismo concepto (imagen, capas, `Dockerfile`) aplica igual para un proyecto en Node, Go o Ruby. Lo que cambia es qué comandos van dentro del `Dockerfile`, no la herramienta en sí.
