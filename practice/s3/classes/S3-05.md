# S3-05 — Seguridad aplicada a las vistas del consultorio

## Contexto

Django protege bastante por defecto — pero "por defecto" no es lo mismo que "a prueba de que vos lo desactivés sin darte cuenta". Esta clase busca vulnerabilidades reales en tu propio código, no en ejemplos de un libro.

## Concepto mínimo

**CSRF — protegido por defecto, roto si lo sacás.** Django exige `{% csrf_token %}` en cada formulario `POST`. Sin él, el request se rechaza. Es fácil de romper accidentalmente copiando un formulario de otro lado sin el token.

**XSS — el escape automático es la norma, `|safe` es la excepción peligrosa.** `{{ variable }}` en una plantilla escapa HTML automáticamente. `{{ variable|safe }}` desactiva ese escape — si esa variable contiene texto que vino de un usuario (por ejemplo, un motivo de cancelación de turno de texto libre), `|safe` abre la puerta a que alguien inyecte HTML o JavaScript que se ejecuta en el navegador de quien lo vea después.

**Inyección SQL — el ORM protege, el SQL crudo no lo hace solo.** Django parametriza automáticamente las consultas hechas con el ORM. Las consultas de `S2-02` (`queries.sql`), si alguna vez se ejecutan desde código Python con datos externos concatenados en el string, necesitan la misma disciplina de parametrización — el ORM no las cubre porque no pasan por él.

**Control de acceso roto — se verifica probando, no leyendo el código.** `S3-04` protegió las vistas con decoradores. Esta clase confirma que la protección funciona intentando activamente saltarla, como lo haría alguien con mala intención, no confiando en que "está el decorador, entonces está bien".

## Demostración

El mentor introduce a propósito una vulnerabilidad real: agrega `|safe` a un campo de "motivo de cancelación" que muestra texto libre ingresado por un usuario, y carga un turno cancelado con un motivo que contiene `<script>alert('vulnerado')</script>` — mostrando el script ejecutándose en el navegador. Saca el `|safe` y repite, mostrando que ahora se ve como texto plano, no se ejecuta.

## Laboratorio

Con guía: sacar deliberadamente `{% csrf_token %}` de un formulario, confirmar que Django rechaza el envío, y restaurarlo.

## Ejercicio

Sin guía: usando el usuario de prueba "Secretaria" de `S2-08` (sin permisos de odontólogo), intentar navegar directamente a cada URL protegida que debería estar fuera de su alcance. Documentar, para cada una, si efectivamente fue bloqueada.

## Challenge

Investigá qué es un IDOR (Insecure Direct Object Reference) y evaluá si el uso de `UUID` como clave primaria (en vez de enteros secuenciales) le da a tu proyecto alguna protección real contra este tipo de ataque, o si es una falsa sensación de seguridad. Documentá tu conclusión con justificación, no solo la respuesta.

## Nota sobre abstracción

Los tres problemas de esta clase (CSRF, XSS, control de acceso) existen en cualquier aplicación web, en cualquier stack. Lo que cambia entre frameworks es cuánta protección viene activada por defecto — Django protege más que muchas alternativas, pero "por defecto" nunca es excusa para no verificar.
