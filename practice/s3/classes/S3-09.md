# S3-09 — Despliegue: proxy inverso y HTTPS

## Contexto

Esta es la clase que cumple la promesa central de `plan.md` para este semestre: al terminarla, el sistema está en un servidor real, con HTTPS real, accesible para gente real — no en tu laptop.

## Concepto mínimo

**El servidor de desarrollo de Django (`runserver`) no está diseñado para producción** — no maneja bien tráfico concurrente ni es seguro exponerlo directamente a internet. En producción corre detrás de un servidor WSGI real, **gunicorn**, que sí está pensado para eso.

**Nginx como proxy inverso.** Nginx recibe el tráfico de internet en el puerto 80/443, y lo reenvía (`proxy_pass`) a gunicorn, que corre en un puerto interno no expuesto directamente. Nginx además sirve los archivos estáticos directamente, sin pasarle esa carga a Django — es más eficiente para eso.

```nginx
server {
    listen 80;
    server_name miconsultorio.com;

    location /static/ {
        alias /app/staticfiles/;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

**HTTPS con certbot (Let's Encrypt).** Certificados gratuitos, renovación automática. Sin HTTPS, cualquier dato que viaje entre el navegador y el servidor —incluidas las cookies de sesión de `S3-04`— es legible por cualquiera en el medio.

## Demostración

El mentor configura gunicorn corriendo la app, Nginx haciendo proxy hacia gunicorn, y corre `certbot` para obtener un certificado real (si hay un dominio disponible) — confirmando con el navegador que el candado de HTTPS aparece y que la conexión es segura de punta a punta.

## Laboratorio

Con guía: configurar Nginx para servir los archivos estáticos directamente (`location /static/`), confirmando con las herramientas de red del navegador que esos archivos ya no pasan por Django.

## Ejercicio

Sin guía: configurar el redirect de HTTP a HTTPS, y confirmarlo con `curl -I http://tu-dominio` viendo el código `301`/`308` hacia la versión HTTPS.

## Challenge

Investigá, sin necesariamente implementarlo, qué cambiaría si en vez de un VPS con Nginx configurado a mano usaras una plataforma administrada (Railway, Fly.io, Render). Documentá el trade-off entre control total y menor esfuerzo operativo — es una decisión real que vas a tener que tomar en algún momento de tu carrera.

## Project Task

1. Servidor real (aunque sea el más barato disponible) con gunicorn + Nginx + HTTPS funcionando.
2. Redirect HTTP → HTTPS confirmado.
3. Archivos estáticos servidos por Nginx, no por Django.
4. Commit de la configuración (no de secretos): `Configurar despliegue con Nginx, gunicorn y HTTPS`.

## Evidencia — Definition of Done

- [ ] El sitio es accesible por HTTPS desde fuera de tu propia red (probado desde otro dispositivo o red, no solo localhost).
- [ ] Una petición HTTP simple redirige automáticamente a HTTPS.
- [ ] Los archivos estáticos se sirven por Nginx, verificado.
- [ ] Es gunicorn el que corre en producción, no `manage.py runserver`.
- [ ] Podés explicar qué hace Nginx y por qué está ahí, con tus palabras.

## Nota sobre abstracción

Proxy inverso, terminación TLS y servidor de aplicación separado del servidor web son conceptos universales de arquitectura de despliegue web, independientes del lenguaje del backend. Nginx es una opción entre varias (Caddy, Apache); el patrón es lo que importa.
