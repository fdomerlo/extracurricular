# S3-08 — Integración continua

## Contexto

Hasta ahora, correr los tests dependía de que vos te acordaras de hacerlo antes de cada commit. Esta clase saca esa responsabilidad de tu memoria: cada vez que subís código, algo lo verifica solo, y si está roto, se ve antes de mergear — no después de que rompió algo en producción.

## Concepto mínimo

**Un workflow de GitHub Actions** es un archivo YAML en `.github/workflows/` que define cuándo correr algo (`on: push`, `on: pull_request`) y qué correr.

```yaml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync
      - run: uv run ruff check .
      - run: uv run pytest
```

Notá `services: postgres` — los tests de `S2` necesitan una base real, no simulada; CI puede levantar un contenedor de Postgres temporal para eso, con el mismo criterio que ya aprendiste en `S3-07`.

**El check tiene que poder fallar de verdad.** Un pipeline de CI que nunca se pone en rojo probablemente no está verificando nada útil.

**Branch protection** (configuración de GitHub, no del workflow) impide mergear a `main` si el check de CI no pasó — cierra el círculo con la disciplina de ramas de `S1-07`: ya no alcanza con que vos "te acuerdes" de no mergear código roto.

## Demostración

El mentor escribe el workflow, hace push de un commit con un error de lint a propósito, muestra el check fallando en rojo en la interfaz de GitHub, lo corrige, y muestra el check pasando en verde.

## Laboratorio

Con guía: agregar el servicio de Postgres al workflow y confirmar que los tests que necesitan base de datos real (de `S2`) pasan en CI, no solo localmente.

## Ejercicio

Sin guía: configurar branch protection en el repositorio para que `main` requiera el check de CI en verde antes de poder mergear — y probarlo intentando mergear una rama con un test roto a propósito, confirmando que GitHub lo bloquea.

## Challenge

Agregá cache de dependencias de `uv` al workflow para acelerar los runs, y medí con los tiempos que muestra GitHub Actions la diferencia entre un run con cache frío y uno con cache tibio.

## Project Task

1. Workflow de CI corriendo lint y tests (con Postgres real) en cada push.
2. Branch protection configurada y probada con un caso real de bloqueo.
3. Commit: `Configurar integración continua con GitHub Actions`.

## Evidencia — Definition of Done

- [ ] El pipeline corre automáticamente en cada push, sin intervención manual.
- [ ] Corre lint y tests, con Postgres real disponible para los tests que lo necesitan.
- [ ] Provocaste un fallo real (lint o test roto) y lo viste rojo en GitHub antes de arreglarlo.
- [ ] Branch protection bloqueó efectivamente un merge con CI en rojo — lo probaste, no lo asumiste.

## Nota sobre abstracción

CI como concepto (verificación automática en cada cambio) es independiente de la plataforma — GitLab CI, CircleCI, Jenkins resuelven lo mismo con sintaxis distinta. La disciplina que importa (nada se mergea sin pasar verificación automática) es transferible completa.
