# S3-01 — HTTP en profundidad: antes del framework

## Contexto

Django va a manejar HTTP por vos de acá en adelante — rutas, métodos, códigos de estado, cookies. Si no entendés qué hay debajo antes de que el framework te lo esconda, cualquier error raro de sesión, de método no permitido, o de redirect que no redirige, se vuelve magia en vez de algo diagnosticable.

## Concepto mínimo

**Ciclo petición-respuesta.** Un cliente (navegador, `curl`) envía una petición con un método, una ruta y headers; el servidor devuelve una respuesta con un código de estado, headers y un cuerpo.

**Métodos, con semántica real, no solo sintaxis.** `GET` no debería tener efectos secundarios (es "seguro") — nunca uses `GET` para cancelar un turno. `POST` crea o ejecuta una acción con efectos. `PUT`/`PATCH` actualizan. Estas convenciones no las hace cumplir nadie automáticamente; las rompés si no las respetás.

**Códigos de estado que importan de verdad:** `200` (éxito), `201` (creado), `302`/`303` (redirect tras un `POST` exitoso — patrón estándar para evitar reenvíos accidentales del formulario), `400` (la petición está mal formada), `401` (no autenticado), `403` (autenticado pero sin permiso), `404` (no existe), `500` (el servidor rompió).

**Cookies y sesión.** El servidor manda `Set-Cookie` en la respuesta; el navegador la devuelve en el header `Cookie` en cada petición siguiente. Así es como Django "sabe" que estás logueado sin que reenvíes tu contraseña en cada request — no hay magia, es un identificador de sesión yendo y viniendo en un header.

## Demostración

El mentor usa `curl -v` contra un servicio de pruebas público (`httpbin.org`) para ver headers reales sin necesitar infraestructura propia:

```bash
curl -v https://httpbin.org/status/404
curl -v -X POST https://httpbin.org/post -d "campo=valor"
curl -v -c cookies.txt https://httpbin.org/cookies/set/sesion/abc123
curl -v -b cookies.txt https://httpbin.org/cookies
```

El último par muestra el ciclo completo: `Set-Cookie` en la primera respuesta, `Cookie` enviada de vuelta en la segunda petición.

## Laboratorio

Con guía: hacer una petición `POST` con datos de formulario contra `httpbin.org/post` y leer la respuesta completa, identificando qué parte del JSON devuelto corresponde a qué parte de la petición original.

## Ejercicio

Sin guía: usando `curl -v` contra `httpbin.org/status/<code>`, provocar y documentar en una tabla corta qué significa cada uno de estos códigos en un contexto real de la agenda del consultorio: `400`, `401`, `403`, `404`, `405`, `500`.

## Challenge

Escribí, con el módulo `socket` de Python (sin ninguna librería HTTP), un servidor mínimo que responda una línea de texto plano a cualquier conexión — para ver con tus propios ojos que HTTP es texto plano sobre TCP, no magia de framework.

## Project Task

No hay código del proyecto real en esta clase — es preparación conceptual. Documentar en una nota corta qué rutas y métodos va a necesitar el consultorio (`GET /agenda`, `POST /turnos`, `POST /turnos/<id>/cancelar`, etc.) antes de escribir la primera vista en `S3-02`.
