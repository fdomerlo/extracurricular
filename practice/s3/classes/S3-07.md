# S3-07 — Compose y entornos

## Contexto

`S3-06` contenerizó la aplicación, pero la aplicación sola no sirve de nada sin la base de datos. Esta clase orquesta los dos servicios juntos, con configuración que cambia entre desarrollo y producción sin tocar código.

## Concepto mínimo

**`docker-compose.yml`** describe varios servicios que corren juntos, en la misma red virtual, donde cada servicio puede llamar a otro por su nombre en vez de `localhost`:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: consultorio
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db_data:/var/lib/postgresql/data

  app:
    build: .
    depends_on:
      - db
    environment:
      DATABASE_URL: postgres://${DB_USER}:${DB_PASSWORD}@db:5432/consultorio
    ports:
      - "8000:8000"

volumes:
  db_data:
```

Notá `db` como host en `DATABASE_URL` — no es un placeholder, es el nombre real del servicio, que Compose resuelve automáticamente.

**Volúmenes persisten datos** más allá del ciclo de vida del contenedor. Sin `db_data:`, cada `docker compose down` borraría la base entera.

**Variables de entorno, nunca hardcodeadas.** `${DB_PASSWORD}` viene de un archivo `.env`, que **nunca se commitea** — se commitea `.env.example` con las claves sin los valores reales, como plantilla.

## Demostración

El mentor levanta ambos servicios con `docker compose up`, muestra la app conectándose a la base por el nombre `db`, y hace `docker compose down` seguido de `up` para mostrar que, gracias al volumen, los datos siguen ahí.

## Laboratorio

Con guía: crear `.env.example` documentando cada variable necesaria, sin valores reales, y confirmar que `.env` está en `.gitignore`.

## Ejercicio

Sin guía: revisar el historial completo de git (`git log -p`) buscando si algún secreto quedó commiteado por error en algún punto anterior del proyecto — y si aparece alguno, investigar cómo se removería del historial (no hace falta ejecutarlo si no hay secretos reales comprometidos, pero sí entender el procedimiento).

## Challenge

Agregá un `healthcheck` al servicio `db` para que Compose espere a que Postgres esté realmente listo para aceptar conexiones antes de iniciar `app` — un bug muy común es que la app arranque antes de que la base esté lista y falle la primera conexión.

## Project Task

1. `docker-compose.yml` completo con `app` y `db`, volumen persistente, variables de entorno.
2. `.env.example` commiteado, `.env` ignorado.
3. `README.md` actualizado: el proyecto completo debe levantarse con `docker compose up` desde un clon limpio.
4. Commit: `Orquestar aplicación y base de datos con Docker Compose`.

## Evidencia — Definition of Done

- [ ] `docker compose up` desde un clon limpio levanta todo sin pasos manuales adicionales.
- [ ] Los datos persisten entre `docker compose down` y `up`.
- [ ] No hay ningún secreto en `.env.example` ni en el historial de git.
- [ ] El `README.md` documenta el comando único de arranque.

## Nota sobre abstracción

Orquestar múltiples servicios con variables de entorno externas es una práctica estándar independiente de la herramienta — Compose es una opción entre varias (Kubernetes para escalas mayores, por ejemplo), pero el patrón de configuración por entorno es universal.
