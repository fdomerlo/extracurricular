# S5-02 — Despliegue y rollback: incluye migraciones

## Contexto

`S3-09` puso el sistema en línea la primera vez. Desde entonces, cada cambio nuevo probablemente se desplegó a mano, con pasos que solo están en tu memoria. Esta clase es la que responde una pregunta que hasta ahora no tuvo que responderse: si un despliegue rompe algo, ¿cómo volvés atrás con confianza, en vez de improvisar?

## Concepto mínimo

**Un procedimiento de despliegue escrito, no recordado.** Traer código nuevo, correr migraciones, recolectar estáticos, reiniciar el servicio de `S5-01` — en ese orden, cada vez, sin depender de la memoria.

```bash
# deploy.sh
git pull origin main
uv sync --frozen
python manage.py migrate
python manage.py collectstatic --noinput
sudo systemctl restart consultorio
```

**Revertir código es fácil. Revertir una migración con datos reales, no siempre.** `python manage.py migrate consultorio 0007` vuelve el esquema a un estado anterior — pero si la migración 0008 borró una columna que ya tenía datos, esos datos no vuelven. Algunas migraciones son seguras de revertir; otras no, una vez aplicadas contra datos reales.

**El patrón expand/contract para cambios riesgosos.** En vez de una sola migración que renombra o elimina algo de golpe: primero agregar lo nuevo sin tocar lo viejo (*expand*), desplegar código que ya usa lo nuevo, confirmar que todo anda bien, y recién en un despliegue posterior eliminar lo viejo (*contract*). Esto hace que cada paso individual sea reversible.

## Demostración

El mentor hace un despliegue real siguiendo `deploy.sh`, con un cambio chico. Después despliega algo deliberadamente roto, y ejecuta el rollback documentado — código revertido con git, servicio reiniciado — mostrando que el sistema vuelve a un estado funcional siguiendo pasos escritos, no improvisando.

## Laboratorio

Con guía: practicar `migrate consultorio <número_anterior>` sobre una migración no destructiva, en un entorno de prueba, confirmando que el esquema vuelve correctamente.

## Ejercicio

Sin guía: diseñar (no necesariamente ejecutar contra producción) una migración que, aplicada directamente, perdería datos si se revirtiera — y documentar cómo se haría en su lugar con el patrón expand/contract, en pasos concretos.

## Challenge

Convertí `deploy.sh` en algo un poco más seguro: que se detenga automáticamente si algún paso falla (`set -e` en el script), en vez de seguir adelante con pasos posteriores sobre una base rota.

## Project Task

1. `deploy.sh` (o `DEPLOY.md`) documentando el procedimiento real usado.
2. Un despliegue y un rollback reales ejecutados siguiendo ese procedimiento, no improvisados.
3. Documentación del patrón expand/contract para el caso del Ejercicio.

## Evidencia — Definition of Done

- [ ] Ejecutaste un despliegue siguiendo el procedimiento documentado, sin pasos improvisados.
- [ ] Ejecutaste un rollback real siguiendo el procedimiento documentado, sin improvisar.
- [ ] Podés explicar por qué algunas migraciones no son seguras de revertir una vez aplicadas contra datos reales.
- [ ] Documentaste un caso concreto de expand/contract para un cambio riesgoso.

## Nota sobre abstracción

El patrón expand/contract para cambios de esquema seguros es independiente del ORM o el motor de base de datos — es una práctica estándar en cualquier sistema que evoluciona su esquema mientras sirve datos reales.
