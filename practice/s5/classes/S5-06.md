# S5-06 — Hardening de aplicaciones

## Contexto

`S3-05` encontró y corrigió vulnerabilidades en el código de las vistas. Esta clase revisa algo distinto: la configuración de producción, que puede exponer el proyecto entero aunque el código esté impecable — el ejemplo más común y más grave es tener `DEBUG = True` activo en producción, lo que expone trazas completas de error, incluida información de configuración, a cualquiera que provoque un error.

## Concepto mínimo

**`manage.py check --deploy`** es un comando de Django que audita automáticamente la configuración de producción contra una lista de buenas prácticas conocidas — es la herramienta correcta para esta clase, no una revisión manual desde cero.

```bash
python manage.py check --deploy
```

Suele señalar: `DEBUG` debe estar en `False`; `ALLOWED_HOSTS` debe estar configurado explícitamente; `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE` y `CSRF_COOKIE_SECURE` deben forzar que las cookies solo viajen por HTTPS; `SECURE_HSTS_SECONDS` debe estar configurado para exigir HTTPS en visitas futuras del navegador.

**Un error en producción no debería mostrar código fuente.** Con `DEBUG = False`, Django muestra una página de error genérica en vez del traceback completo — verificar esto activamente, no asumir que el `.env` de producción ya lo tiene bien puesto.

**Rate limiting en el login, a nivel de Nginx.** `S3-04` protegió el acceso con permisos, pero no limitó cuántos intentos de login puede hacer alguien en poco tiempo — sin eso, un ataque de fuerza bruta contra la contraseña de un usuario real es viable.

## Demostración

El mentor corre `manage.py check --deploy` contra la configuración real de producción, y corrige cada advertencia una por una hasta que el comando no reporta nada.

## Laboratorio

Con guía: configurar `limit_req` en Nginx sobre la ruta de login, limitando la cantidad de intentos por minuto desde una misma dirección.

## Ejercicio

Sin guía: provocar un error real en producción (por ejemplo, una URL que no existe con un parámetro raro) y confirmar que la respuesta es una página de error genérica, sin traza de código ni configuración expuesta.

## Challenge

Investigá qué agregaría un header `Content-Security-Policy`, y documentá si se justifica implementarlo ahora o si queda como trabajo futuro — mismo criterio de `S4-06`.

## Project Task

1. `manage.py check --deploy` sin advertencias pendientes.
2. Rate limiting configurado y probado en el endpoint de login.
3. Confirmación real (no asumida) de que `DEBUG = False` en producción.

## Evidencia — Definition of Done

- [ ] `manage.py check --deploy` no muestra advertencias.
- [ ] Provocaste un error real en producción y confirmaste que no expone código ni configuración.
- [ ] El rate limiting del login fue probado con intentos repetidos reales, no solo configurado.

## Nota sobre abstracción

Cada framework tiene su propia lista de configuraciones de producción críticas — la de Django no es transferible palabra por palabra a otro framework, pero la categoría de riesgo (configuración de desarrollo filtrada a producción) es universal.
