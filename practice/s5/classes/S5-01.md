# S5-01 — Linux y redes para el servidor

## Contexto

`S3-09` dejó el sistema corriendo, pero probablemente corriendo de una forma frágil: gunicorn arrancado a mano, en una terminal que si se cierra, se lleva el proceso con ella. Esta clase resuelve algo que quedó pendiente sin decirlo explícitamente en `S3`: ¿el sistema vuelve a andar solo si el servidor se reinicia?

## Concepto mínimo

**`systemd` administra procesos como servicios del sistema operativo**, no como comandos sueltos en una terminal. Un servicio de `systemd` arranca automáticamente al bootear, se reinicia solo si el proceso muere, y se controla con comandos estándar (`start`, `stop`, `status`, `restart`).

```ini
# /etc/systemd/system/consultorio.service
[Unit]
Description=Consultorio - gunicorn
After=network.target

[Service]
User=consultorio
WorkingDirectory=/opt/consultorio
ExecStart=/opt/consultorio/.venv/bin/gunicorn consultorio.wsgi --bind 127.0.0.1:8000
Restart=always

[Install]
WantedBy=multi-user.target
```

**SSH con clave, no con contraseña.** Una contraseña se puede forzar por fuerza bruta; una clave privada, prácticamente no. Deshabilitar autenticación por contraseña en SSH es de las medidas de mayor impacto por menor esfuerzo que existen.

**Firewall mínimo.** Solo los puertos que el sistema realmente necesita expuestos: `22` (SSH), `80`/`443` (HTTP/HTTPS). Todo lo demás, cerrado — incluido el puerto donde corre gunicorn internamente, que no debería ser accesible desde afuera, solo desde Nginx en la misma máquina.

**Comandos de diagnóstico básicos:** `journalctl -u consultorio` para ver los logs del servicio, `systemctl status consultorio` para el estado actual, `df -h` para espacio en disco, `top`/`htop` para procesos y uso de recursos.

## Demostración

El mentor crea el archivo de servicio de `systemd`, lo habilita (`systemctl enable consultorio`), y **reinicia el servidor de verdad** (o lo simula de la forma más realista posible) — mostrando que el sistema vuelve a estar disponible sin que nadie haga nada manualmente.

## Laboratorio

Con guía: configurar autenticación SSH por clave y deshabilitar la autenticación por contraseña, confirmando que el acceso por clave sigue funcionando antes de cerrar la puerta a la contraseña.

## Ejercicio

Sin guía: configurar un firewall (`ufw` u equivalente) que permita solo los puertos necesarios, y verificar desde afuera del servidor (no desde adentro) que los demás puertos efectivamente no responden.

## Challenge

Investigá `fail2ban` como protección adicional contra intentos repetidos de acceso por SSH, y evaluá si se justifica agregarlo ahora o si alcanza con lo ya configurado — mismo criterio de `S4-06`.

## Project Task

1. Servicio de `systemd` para gunicorn, habilitado y probado con un reinicio real del servidor.
2. SSH configurado por clave, sin autenticación por contraseña.
3. Firewall configurado y verificado desde afuera.
4. `RUNBOOK.md` documentando los comandos básicos de diagnóstico y operación del servidor.

## Evidencia — Definition of Done

- [ ] El sistema volvió a estar disponible automáticamente después de un reinicio real del servidor, sin intervención manual.
- [ ] La autenticación SSH por contraseña está deshabilitada, y la de clave funciona.
- [ ] El firewall permite solo los puertos necesarios, verificado desde afuera.
- [ ] `RUNBOOK.md` documenta cómo revisar el estado y los logs del servicio sin tener que buscarlo cada vez.

## Nota sobre abstracción

`systemd` es específico de distribuciones Linux modernas (no todas lo usan), pero el concepto —gestionar procesos como servicios del sistema operativo, con reinicio automático— existe en cualquier sistema operativo de servidor, con su propio mecanismo equivalente.
