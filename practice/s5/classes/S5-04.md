# S5-04 — Secrets y gestión de identidades

## Contexto

`S3-07` ya estableció que los secretos viven en `.env`, no en el código. Esta clase va un paso más allá: quién y qué, dentro del servidor mismo, tiene acceso a esos secretos y a qué puede hacer con ellos — y por qué correr la aplicación como el usuario más privilegiado del sistema (`root`) es un riesgo innecesario.

## Concepto mínimo

**Principio de menor privilegio.** El proceso que corre la aplicación no necesita ser `root` — necesita exactamente los permisos para leer su propio código, escribir sus propios logs, y conectarse a la base de datos. Un usuario dedicado, sin privilegios de administrador, limita el daño posible si algo sale mal.

**Rotación de secretos, sin downtime.** Cambiar una contraseña de base de datos no debería requerir planear una ventana de mantenimiento — actualizar el valor en `.env`, reiniciar el servicio (`S5-01`), confirmar que sigue funcionando, y confirmar que el valor anterior ya no sirve.

**Gestión de accesos SSH.** Con el tiempo, es fácil perder de vista quién tiene acceso a un servidor — claves que se agregaron para depurar algo puntual y nunca se sacaron. Auditar periódicamente `~/.ssh/authorized_keys` y quitar lo que ya no corresponde.

## Demostración

El mentor confirma con qué usuario corre hoy el proceso de la aplicación (`ps aux | grep gunicorn`), y si es `root` u otro usuario con privilegios de más, migra el servicio de `systemd` (`S5-01`) para correr con un usuario dedicado sin privilegios administrativos.

## Laboratorio

Con guía: rotar la contraseña de la base de datos — actualizar en Postgres, actualizar `.env`, reiniciar el servicio, confirmar que funciona con la nueva y que la vieja ya no sirve.

## Ejercicio

Sin guía: auditar el archivo `authorized_keys` del servidor, documentar cada clave presente y a quién corresponde, y remover cualquiera que no debería seguir teniendo acceso.

## Challenge

Investigá una herramienta de gestión de secretos más allá de `.env` (por ejemplo, `pass`, o el gestor de secretos de tu proveedor de nube si usás uno) y evaluá, con el mismo criterio de `S4-06`, si se justifica adoptarla ahora o si `.env` sigue siendo suficiente para la escala actual del proyecto.

## Project Task

1. La aplicación corre con un usuario dedicado, sin privilegios de `root`, confirmado.
2. Contraseña de base de datos rotada exitosamente, sin downtime.
3. Auditoría de accesos SSH documentada.

## Evidencia — Definition of Done

- [ ] Confirmaste, no asumiste, con qué usuario corre el proceso de la aplicación — y no es `root`.
- [ ] Rotaste un secreto real sin interrumpir el servicio, y confirmaste que el valor anterior dejó de funcionar.
- [ ] Documentaste quién tiene acceso SSH al servidor y por qué.

Principio de menor privilegio y rotación de secretos son prácticas universales de seguridad operativa, sin relación con el stack de la aplicación — aplican igual sea cual sea el lenguaje o framework.
