
### Assessment Framework

Cómo se evalúa una competencia

### Filosofía

El estudiante no aprueba por asistir ni por completar lecturas.

Cada competencia requiere una evidencia observable.

### Tipos de evidencia

| Código | Evidencia         |
| ------ | ----------------- |
| E1     | Laboratorio       |
| E2     | Ejercicio         |
| E3     | Challenge         |
| E4     | Proyecto          |
| E5     | Code Review       |
| E6     | Defensa oral      |
| E7     | Pull Request      |
| E8     | Documento técnico |

### Criterio de aprobación por módulo

Cada módulo debe cumplir cuatro condiciones:

Implementación funcional

Tests suficientes

Explicación técnica

Integración con el proyecto

### Rúbrica

|Dimensión|Peso|
|---|---|
|Correctitud|30%|
|Diseño|20%|
|Testing|15%|
|Legibilidad|15%|
|Diagnóstico|10%|
|Comunicación|10%|

### Política de IA

|Semestre|Permitido|
|---|---|
|S1|Tutor, explicación y debugging|
|S2|SQL, tests y revisión|
|S3|Boilerplate y documentación|
|S4|Refactoring y Code Review|
|S5|Diagnóstico operativo|
|S6|Agentes y desarrollo por especificación|

### Regla inmutable

> Todo código incorporado al proyecto debe poder ser explicado, modificado y defendido por el estudiante.

### Checklist de egreso

Un estudiante egresa cuando puede demostrar:

- Diseñar un dominio desde cero.
- Resolver concurrencia correctamente.
- Construir una aplicación web completa.
- Escribir tests de distintos niveles.
- Dockerizar y desplegar el sistema.
- Automatizar CI/CD.
- Diagnosticar un incidente usando logs.
- Trabajar sobre código ajeno.
- Contribuir mediante Pull Requests.
- Utilizar IA de forma verificable y responsable.
